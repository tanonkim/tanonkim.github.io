## Context

`context`는 전역으로 전달되어야 하는 값을 prop drilling없이 안전하게 전달하기 위한 도구

이다.

### 개념

createContext로 생성하고, Provider로 공급하며, useContext로 소비한다.

목적 : 여러 단계로 내려가는 props 전달 (prop drilling 회피)

단점 : Provider가 가진 값이 바뀌면 그 Provider 아래 모든 useContext를 사용하는 컴포넌트가 재렌더링된다. → 성능에 주의해야 한다.

### Method

1. React.createContext

   ```tsx
   const MyContext = React.createContext(defaultValue);
   ```

   Context 객체를 구독하고 있는 컴포넌트를 렌더링할 때 가장 가까이 있는 Provider로 부터 현재 값을 얻는다.

   defaultValue 매개변수는 트리 안에서 적절한 Provider를 찾지 못했을 때만 쓰이는 값이다.

2. Context.Provider

   ```tsx
   <MyContext.Provider value={/* 어떤 값 */}>
   ```

   Context 오브젝트에 포함된 React 컴포넌트인 **Provider**는 context를 구독하는 컴포넌트에게 context의 변화를 알리는 역할을 한다.

3. Context.Consumer

   ```tsx
   <MyContext.Consumer>
     {value => /* context 값을 이용한 렌더링 */}
   </MyContext.Consumer>
   ```

   context 변화를 구독하는 React 컴포넌트이다. 이 컴포넌트를 사용하면 함수 컴포넌트 안에서 context를 구독할 수 있다.

   이 함수가 받는 value 매개변수 값은 해당 context의 Provider 중 가장 가까운 Provider의 value prop과 동일하다.

   useContext로 대체가 가능하다.

4. React.useContext

   ```tsx
   const value = useContext(MyContext);
   ```

   context 객체를 받아 그 context의 현재값을 반환한다. context의 현재 값은 트리 안에서 이 Hook을 호출하는 컴포넌트에 가장 가까이 있는 <MyContext.Provider>의 value prop에 의해 결정된다.

   - **맞는 사용:** useContext(MyContext)
   - **틀린 사용:** useContext(MyContext.Consumer)
   - **틀린 사용:** useContext(MyContext.Provider)

### TS에서 Context를 만들 때의 기본 패턴

1. context 타입을 정의하고 createContext<T | undefined>(undefined)로 만든 뒤, 전용 Hook(useXXX)을 만들어 undefined 체크 후 에러를 던진다.
   1. Provider 내부 값은 useMemo로 묶어 identity를 안정화한다.

### 예제1 : ThemeContext

예) src/context/ThemeContext.tsx

```tsx
import React, { createContext, useContext, useMemo, useState } from "react";

export type Theme = "light" | "dark";

interface ThemeContextType {
  theme: Theme;
  setTheme: (t: Theme) => void;
  toggle: () => void;
}

const ThemeContext = createContext<ThemeContextType | undefined>(undefined);

export const ThemeProvider: React.FC<{ children: React.ReactNode }> = ({
  children,
}) => {
  const [theme, setTheme] = useState<Theme>(() => {
    try {
      const stored = localStorage.getItem("theme") as Theme | null;
      return stored ?? "light";
    } catch {
      return "light";
    }
  });

  const toggle = () => {
    setTheme((t) => {
      const next = t === "light" ? "dark" : "light";
      try {
        localStorage.setItem("theme", next);
      } catch {}
      return next;
    });
  };

  // 불필요한 재렌더링 줄이기
  const value = useMemo(() => ({ theme, setTheme, toggle }), [theme]);

  return (
    <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>
  );
};

export const useTheme = (): ThemeContextType => {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme must be used within ThemeProvider");
  return ctx;
};
```

예) src/components/ThemeToggle.tsx

```tsx
import React from "react";
import { useTheme } from "../context/ThemeContext";

export const ThemeToggle: React.FC = () => {
  const { theme, toggle } = useTheme();
  return (
    <div className="card">
      <p>
        현재 테마: <strong>{theme}</strong>
      </p>
      <button onClick={toggle}>토글 테마</button>
    </div>
  );
};
```

### 예제2 : AuthContext with 선택적 구독 패턴

액션타입, 상태, reducer, async login 함수를 포함, state와 action을 분리하는 패턴 → 재렌더링 최소화

예) src/context/AuthContext.tsx

```tsx
import React, {
  createContext,
  useContext,
  useEffect,
  useReducer,
  useCallback,
} from "react";

type User = {
  id: string;
  name: string;
  email: string;
};

type AuthState = {
  user: User | null;
  token: string | null;
  loading: boolean;
  error: string | null;
};

type AuthAction =
  | { type: "INIT"; payload: { user: User | null; token: string | null } }
  | { type: "LOGIN_START" }
  | { type: "LOGIN_SUCCESS"; payload: { user: User; token: string } }
  | { type: "LOGIN_FAILURE"; payload: string }
  | { type: "LOGOUT" };

const initialState: AuthState = {
  user: null,
  token: null,
  loading: false,
  error: null,
};

function authReducer(state: AuthState, action: AuthAction): AuthState {
  switch (action.type) {
    case "INIT":
      return {
        ...state,
        user: action.payload.user,
        token: action.payload.token,
      };
    case "LOGIN_START":
      return { ...state, loading: true, error: null };
    case "LOGIN_SUCCESS":
      return {
        ...state,
        loading: false,
        user: action.payload.user,
        token: action.payload.token,
      };
    case "LOGIN_FAILURE":
      return { ...state, loading: false, error: action.payload };
    case "LOGOUT":
      return { ...initialState };
    default:
      return state;
  }
}

const AuthStateContext = createContext<AuthState | undefined>(undefined);
const AuthDispatchContext = createContext<
  | {
      login: (email: string, password: string) => Promise<void>;
      logout: () => void;
    }
  | undefined
>(undefined);

export const AuthProvider: React.FC<{ children: React.ReactNode }> = ({
  children,
}) => {
  const [state, dispatch] = useReducer(authReducer, initialState);

  useEffect(() => {
    try {
      const token = localStorage.getItem("token");
      const userJson = localStorage.getItem("user");
      const user = userJson ? (JSON.parse(userJson) as User) : null;
      if (token && user) {
        dispatch({ type: "INIT", payload: { user, token } });
      }
    } catch {
      // ignore
    }
  }, []);

  const login = useCallback(async (email: string, password: string) => {
    dispatch({ type: "LOGIN_START" });
    try {
      // Simulate API call
      await new Promise((r) => setTimeout(r, 500));
      const fakeToken = "fake-token-123";
      const user = { id: "1", name: "Jane Doe", email };
      localStorage.setItem("token", fakeToken);
      localStorage.setItem("user", JSON.stringify(user));
      dispatch({ type: "LOGIN_SUCCESS", payload: { user, token: fakeToken } });
    } catch (err) {
      dispatch({ type: "LOGIN_FAILURE", payload: "Login failed" });
    }
  }, []);

  const logout = useCallback(() => {
    localStorage.removeItem("token");
    localStorage.removeItem("user");
    dispatch({ type: "LOGOUT" });
  }, []);

  return (
    <AuthStateContext.Provider value={state}>
      <AuthDispatchContext.Provider value={{ login, logout }}>
        {children}
      </AuthDispatchContext.Provider>
    </AuthStateContext.Provider>
  );
};

export const useAuthState = (): AuthState => {
  const ctx = useContext(AuthStateContext);
  if (!ctx) throw new Error("useAuthState must be used within AuthProvider");
  return ctx;
};

export const useAuthActions = () => {
  const ctx = useContext(AuthDispatchContext);
  if (!ctx) throw new Error("useAuthActions must be used within AuthProvider");
  return ctx;
};
```

예) src/components/Auth.tsx

```tsx
import React from "react";
import { useAuthActions, useAuthState } from "../context/AuthContext";

export const LoginForm: React.FC = () => {
  const { login } = useAuthActions();
  const { loading, error } = useAuthState();

  const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault();
    // 샘플 고정 값으로 로그인 시도
    await login("test@example.com", "password");
  };

  return (
    <form onSubmit={handleSubmit} className="card">
      <button type="submit" disabled={loading}>
        {loading ? "로그인 중..." : "로그인 (샘플)"}
      </button>
      {error && <div style={{ color: "red" }}>{error}</div>}
    </form>
  );
};

export const Profile: React.FC = () => {
  const { user } = useAuthState();
  const { logout } = useAuthActions();
  if (!user) return <div className="card">로그인 필요</div>;
  return (
    <div className="card">
      <p>
        <strong>{user.name}</strong> ({user.email})
      </p>
      <button onClick={logout}>로그아웃</button>
    </div>
  );
};
```

1. state, actions를 분리한 두 컨텍스트를 사용하면 login함수가 바뀌지 않는 한 state 변경에 의해 login을 사용하는 컴포넌트가 불필요한 리렌더를 줄이 수 있다.
2. 비동기 액션 : Provider내부에서 정의, useCallback으로 감싸서 stable reference 유지

---

- 작은 value : \*\*\*\*Provider가 제공하는 값의 객체가 자주 바뀌면 아래 모든 consumer가 리렌더된다. `useMemo`/`useCallback`으로 안정화하기.
- 선택적 구독 (selector 패턴): 필요하면 컨텍스트에서 여러 훅을 제공(예: `useAuthUser`, `useAuthLoading`)하여 소비 컴포넌트가 실제로 필요한 값만 읽게 한다.

### 언제 Context 대신에 라이브러리를 고려할까?

Context는 좋지만, 아래의 경우엔 상태관리 라이브러리를 고려하는 것도 좋다.

- 빈번한 작은 작은 업데이트가 많이 성능 이슈가 날 때
- 복잡한 상태 의존성/미들웨어가 필요할 때
- 여러 플랫폼/비동기 백엔드와 고도로 통합된 구조(서버 상태 캐싱 등) - React Query, SWR 등 사용
- 전역 상태를 더욱 간결하고 성능 좋게 다루고 싶을 때 : Zustand, Jotai 등 경량 대안

단순 globalish한 데이터엔 Context가 충분하다.

### 안티패턴

- 거대한 Root Context 하나에 모든 상태 넣기 → 빨리 복잡해지고 불필요한 리렌더링이 발생한다.
- Provider value에 매 렌더마다 함수/객체를 새로 생성하기 → X
- lazy initialization없이 큰 초기화 로직을 Provider 렌더 경로에 넣기
