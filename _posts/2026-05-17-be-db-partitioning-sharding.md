### 대용량 테이블

데이터 - 수천만~수억건

모든 요청이 단일 DB로 모임

비효율적인 쿼리 (인덱스 X, 풀테이블 스캔)

→ 처음부터 확장성에 대한 고려가 없기 때문

## 1. 파티셔닝

하나의 큰 테이블을 여러개의 작은 물리적 조각으로 나눔

Order 테이블 → 2022년~2025년 10억건 → 2022년, 2023년, 2024년, 2025년

⇒ 디스크 I/O 최적화

- Range Partitioning
  - 연속적인 범위, 예) 2022년, 2023년, 2024년, 2025년 …
- List Partitioning
  - 명확한 카테고리, 예) 의류, 전자제춤, 식품, 도서
- Hash Partitioning
  - 해시 함수로 데이터를 균등하게 분산, 예)

    ![](/assets/img/2026-05-17/be-db-partitioning-sharding-1.png)

### 트레이드 오프

복잡도 증가 (여러 파티션 관리 / Range 관리)

쿼리 성능 저하 가능 (키가 아닌 컬럼으로 검색 시, 모든 파티션 검색 스캔)

초기 설정 어려움 (파티션 키 변경이 매우 어려움, 처음부터 신중한 설계)

해시 범위 검색 X

## 2. 샤딩

단일 DB 부하 방지

여러개의 독립적인 DB 서버로 데이터 분산 → 부하 분산 + 확장성 (완전히 다른 물리적 DB)

![](/assets/img/2026-05-17/be-db-partitioning-sharding-2.png)

각 서버 부담 → 1/N

트래픽이 늘어나면 Shard 하나 추가 가능 (수평 확장 가능)

일부 장애 시 나머지는 정상 작동

### 트레이드 오프

복잡도가 기하급수적으로 증가 (여러 서버 관리)

애플리케이션 로직 구현 (어느 Shard로 갈지 구현)

**조인이 거의 불가능 (다른 Shard 데이터 조인 불가)**

- 사용자정보 : Shard1, 주문정보 : Shard2 → 메모리에서 조합해야 함

트랜잭션 처리 어려움 (ACID 보장 어려움)

- 분산트랜잭션 구현이 복잡함

Shard 재배치 고난이도

- 4개 → 8개로 확장 시 전체 데이터 재배치
- 무중단 재배치는 매우 어렵다

HotSpot 문제

- 특정 Shard에만 집중 가능 → 과부하

### 언제 해야 하나

CPU, 메모리, DiskIO 등 더이상 스케일업이 불가능하다면 그 때 진행

단일DB → Master/Slave → 인덱싱 등 최적화, 캐싱 → Partitioning → Sharding (최후)
