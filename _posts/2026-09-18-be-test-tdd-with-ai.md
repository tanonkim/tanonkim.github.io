## TDD란

TDD(Test Driven Development)는 "테스트를 먼저 쓰는 것"이 아니다. 기대값을 먼저 확정하고, 그 기대값이 실패하는 것을 본 뒤에 구현하는 것이다.

아래 두가지가 핵심이다.

- 기대값을 사람이 정한다 : 구현이 정답을 정하지 못하게 한다.
- 실패를 눈으로 본다 : 그 테스트가 무엇을 막는지 증거를 남긴다.

### 사이클 3단계

| 단계 | 하는 일 | 지켜야 하는 것 |
| --- | --- | --- |
| RED | 기대값을 테스트로 쓰고, 실패를 확인 | 컴파일 에러, NPE는 RED가 아님. 타입, 메서드를 만들어 컴파일 된 상태에서 assertion 실패를 본다. 실패 이유가 기능이 없어서인지 확인한다. |
| GREEN | 그 테스트를 통과시키는 가장 단순한 구현 | 아직 요구하지 않은 일반화를 넣지 않는다. 실패하면 코드를 고친다. 기대값을 고치지 않기. |
| REFACTOR | 동작을 유지하며, 중복/책임/네이밍 등 정리 | 행동을 추가하지 않는다. refactoring이라 정리할 게 없으면 pass |

### 이번 포인트 사례에서 TDD를 적용하면서 매핑을 한다면

포인트를 설계한 방식은 아래와 같다.

**RED** : `expected: Money[amount=0] but was: Money[amount=3000]` ← 넣은 순서대로 차감해서 실패

기대값은 B의 5000원을 다 쓰고 남은 7000원을 A에서 사용하므로 : B는 0원, A는 3000원(A부터 차감했다)

```java
PointGroup groupA = groupChargedAt(10_000, 2025);  // 2030-01-01 만료 (늦게 만료)
PointGroup groupB = groupChargedAt(5_000, 2024);   // 2029-01-01 만료 (먼저 만료)

// A → B 순서로 넘기고 12,000원을 결제한다
List<PointUsage> usages = policy.pay(List.of(groupA, groupB), Money.of(12_000), NOW);

assertThat(groupB.getRemaining()).isEqualTo(Money.of(0));       // B를 먼저 다 쓴다
assertThat(groupA.getRemaining()).isEqualTo(Money.of(3_000));   // 나머지를 A에서
assertThat(usages).extracting(PointUsage::group, PointUsage::amount)
    .containsExactly(tuple(groupB, Money.of(5_000)), tuple(groupA, Money.of(7_000)));
```

**GREEN** : 루프 전에 만료 시각 순으로 정렬

루프 안을 어떻게 고쳐도 A를 먼저 만나는 것은 바뀌지 않는다. 순회 순서 변경이 필요

```java
List<PointGroup> byExpiry = groups.stream()
    .sorted(Comparator.comparing(PointGroup::getExpiresAt))   // 만료 시각 오름차순
    .toList();
for (PointGroup group : byExpiry) { ... }
```

PNT-05 불변식에는 "만료 시각이 같으면 먼저 충전한 그룹부터"라는 조건도 있지만, 이 테스트가 요구하지 않아서 넣지 않았다. 요구하지 않은 것을 넣지 않는 것이 Green의 규칙.

**REFACTOR** : 변수 네이밍 수정 `byExpiry` → `usableByExpiry`

두 바퀴를 더 돌면서 코드가 아래처럼 변했다.

```java
List<PointGroup> byExpiry = groups.stream()
    .filter(group -> group.isUsableAt(now))                    // ← 세 번째 바퀴에서 추가
    .sorted(Comparator.comparing(PointGroup::getExpiresAt))
    .toList();
```

filter가 붙으면서 이 목록의 뜻이 바뀌었습니다. (지금 쓸 수 있는 그룹만 + 만료 시각 순, 기존 : 만료 시간 순으로 정렬)

이름 하나만 바꾼 것이지만 변수를 읽는 사람은 여기엔 만료된 그룹이 없다는 사실을 바로 알게 된다.

Refactor에서는 동작을 변경하지 않고, 이름과 주석을 추가 및 변경했고, 테스트를 돌려 모두 Green(Pass)를 확인했다.

### 기존 방식(테스트를 구현 이후에 작성)과 무엇이 다른가

| 항목 | 기존 → TDD |
| --- | --- |
| 기대값 출처 | 이미 돌아가는 구현을 보고 작성 → 구현 전에 직접 정한다. |
| 그 테스트가 뭘 막는지 | 모른다 → 실패를 봤으니 안다 |
| 설계 | 테스트를 하기 어려운 코드가 그대로 남는다. → 테스트하기 쉬운 쪽으로 설계가 바뀐다. (클래스 구조 개선, 하나의 클래스에 너무 많은 책임을 지니거나, 또는 책임이 없거나 → 이를 방지한다.) |
| 범위 | 기존은 한번에 많이 만들고 마지막에 검증한다 → TDD에서는 한번에 행동 하나를 한다. |

### TDD 장단점

**장점**

- 실패를 본 테스트만 남으니 테스트를 믿을 수 있다
- 기대값이 문서가 된다 (`@DisplayName`에 규칙 ID를 적었다)
- 거절·경계 사례를 먼저 쓰게 되어 예외 처리가 빠지지 않는다
- 책임이 테스트 준비 크기로 드러난다 (너무 많은 책임이나, 책임이 없거나 그런 경우는 사라질 것.)

**단점**

- 느릴 수 있다. 한 규칙에 사이클을 여러 번 돌기 때문에. 그치만 더 정확할 수 있다.
- 모든 코드에 맞지 않는다. 설정, 단순 DTO 매핑은 대상이 아니다
- 테스트도 유지비가 있다. 잘못 쓴 테스트는 오히려 발목을 잡는다
- RED를 만들기 어려운 경우가 있다 (트랜잭션 롤백 같은 것)

## 요즘시대 AI에게 구현을 맡기면 TDD가 의미가 있을까

"이런 테스트로 RED-GREEN-REFACTOR를 해야겠다" 했는데, 지금은 구현을 AI에게 맡기고 있다. 그래서 스스로 의심이 들었다. 이래도 TDD가 의미가 있을까.

⇒ 의미가 분명 있다. 다만 무게 중심이 옮겨가야 한다.

AI는 기대값을 주면 테스트와 정답 구현을 같이 쓴다. 그러면 RED가 아예 생기지 않는다. 실패를 한 번도 본 적 없는 테스트만 남는다. 그래서 두 가지를 직접 쥐어야 했다.

- **기대값은 내가 만든다.** 구현과 평가 기준을 같은 쪽에 맡기지 않는다.
- **RED를 잘 만든다.** 기대값 목록을 먼저 합의하고, 일부러 틀린 최소 구현을 남겨둔 상태에서 테스트를 돌린다.

그리고 AI와의 핑퐁이 오히려 더 값어치 있는 지점이 있다. 경우를 같이 세는 일이다. 사람 혼자 생각하면 정상 경로 위주로 떠오르는데, 상황을 구체적으로 주고받으면 생각하지 못한 경우까지 나온다. 만료 직전과 정각, 0원, 저장 범위 초과 같은 것들이 그렇게 나왔다.

그러려면 컨텍스트가 충분히 전달되어야 한다. 무엇을 줘야 하는지 정리하면 아래와 같을 것 이다.

1. **용어** — 그룹·지갑·남은 금액·만료 시각처럼 이 도메인의 말
2. **규칙과 기대값** — 규칙 ID와 입력 → 기대 결과, 숫자까지
3. **흐름** — 누가 누구에게 무엇을 묻는지, 확인과 변경의 순서
4. **경우의 조합** — 만료된 것만 / 유효한 것만 / 섞인 경우 / 경계(정각) / 0원
5. **각 테스트가 잡을 잘못된 구현** — 하나가 아니라 둘 이상 지어내 본다

## 초록인데 규칙을 지키지 않던 테스트

우리는 1~3은 문서로 합의했다. 그런데 4와 5에서 구멍이 났다.

만료 시각이 지난 그룹은 없는 셈 친다(PNT-07). 잔액에서도 빠지고 결제에도 쓰이지 않는다. 기대값은 이렇게 적어 뒀다.

> W-7 · 만료된 그룹만 있을 때 결제 → 거절

```java
// 만료된 A(4,000원)만 있을 때 1,000원 결제 → 거절, A의 남은 금액은 그대로
PointGroup groupA = expiredGroup(4_000);

assertThatThrownBy(() -> policy.pay(List.of(groupA), Money.of(1_000), NOW))
    .isInstanceOf(CoreException.class)
    .extracting("errorType").isEqualTo(ErrorType.CONFLICT);
assertThat(groupA.getRemaining()).isEqualTo(Money.of(4_000));
```

통과했다. 만료 규칙이 지켜진다고 생각했다. 그런데 만료를 거르는 코드가 없었다.

만료 검사는 `PointGroup`이 하고 있었다.

```java
public void use(Money usage, ZonedDateTime now) {
    if (!isUsableAt(now)) {
        throw new CoreException(ErrorType.CONFLICT, "만료된 포인트는 사용할 수 없습니다.");
    }
    ...
}
```

서로 다른 두 동작이 있었고, W-7 테스트에서는 결과가 같았다.

이게 실제로 만드는 버그 : 조용히 틀린 게 아니라 결제를 막는다. 그룹 조회는 만료 시각이 이른 순이라 만료된 그룹이 목록 맨 앞에 온다.

- 5년 전 충전분 4,000원이 만료된 채 남아 있고, 어제 10,000원을 충전한 사용자
- 잔액 조회는 10,000원을 보여 준다 (잔액 계산은 만료 그룹을 제대로 거른다)
- 그런데 1,000원 결제가 거절된다

잔액은 있다는데 결제는 안 되는 상태다. 주문 확정 API에 연결하기 전에 발견해서 운영에 나가지는 않았다. 나갔다면 QA가 만료된 포인트가 남아 있는 사용자를 만들어 보지 않는 한 재현되지 않는다.

### 왜 못 잡았나

용어·규칙·흐름은 AI와 이미 계약(?)합의 했다. 컨텍스트의 문제로, 부족했던 건 용어나 흐름이 아니라 경우의 조합과 기대값의 정밀도였다.

섞인 경우를 추가하니 RED가 발생하였다.

```java
// 만료된 A(4,000) + 유효한 B(5,000), 1,000원 결제 → 성공해야 한다 (B에서만)
PointGroup groupA = expiredGroup(4_000);
PointGroup groupB = usableGroup(5_000);

List<PointUsage> usages = policy.pay(List.of(groupA, groupB), Money.of(1_000), NOW);

assertThat(groupB.getRemaining()).isEqualTo(Money.of(4_000));
assertThat(groupA.getRemaining()).isEqualTo(Money.of(4_000));   // A는 건드리지 않는다
assertThat(usages).extracting(PointUsage::group, PointUsage::amount)
    .containsExactly(tuple(groupB, Money.of(1_000)));
```

같은 방법으로 만료 그룹 필터 제거, 잔액과 같은 금액도 거절, 0원 사용 건너뛰기 제거 등등 제품 코드를 하나씩 망가뜨려 보니 빈 곳이 더 있었다.

그리고 반대 방향의 구멍도 있었다 : RED를 봤다고 테스트가 옳은 것도 아니었다.

내가 쓴 assertion 중에 이런 게 있었다.

```java
.containsExactly(tuple(groupB, 5000), tuple(groupA, 7000));   // 꺼낸 값은 Money인데 정수와 비교
```

이건 맞는 구현에서도 실패하는 테스트다. 그런데 앞줄에서 먼저 실패해서 가려져 있었다. 테스트코드는 처음 실패한 줄에서 멈추기 때문에, 뒤의 줄은 한 번도 실행되지 않았다.

### 이 구멍을 찾은 방법

테스트가 찾아 준 게 아니다. 코드를 읽다가 찾았다. 만료 규칙이 어디서 지켜지는지 눈으로 따라가다가 `pay()`에 그 판단이 없다는 걸 봤다. 테스트는 그다음에 증명해 줬을 뿐이다.

## 그래서 테스트를 쓸 때 스스로 묻는 질문

> 이 테스트를 통과하는 틀린 구현을 하나 더 지어낼 수 있는가?
>
> 지어낼 수 있으면 그 테스트는 아직 부족하다.

거절을 기대하는 테스트는 특히 의심해야 한다. 거절로 가는 길이 여러 개면 엉뚱한 길로 거절돼도 초록이다. 그래서 "그 조건 하나만 빼면 성공하는" 짝이 필요하다.

이 질문은 결국 서비스의 신뢰성 이야기다. 테스트가 203개 통과한다는 문장은 203개가 무엇을 막고 있는지 모르면 아무 약속도 하지 못한다. 잔액은 있다는데 결제가 안 되는 서비스를 만들어 두고도 Green을 보고 있었을 수 있다.

> AI가 코드를 짜더라도 변경된 코드를 깊이 이해하려고 노력하고, 보수적으로 접근한다. 개인 프로젝트에서도 클래스 다이어그램, 모듈 구조, 코드 라인 단위까지 보면서 큰 그림을 그리려 한다. 기준은 "내가 이 코드를 유지보수할 수 있을 정도로 이해했는가"이다.

멘토님께서 말씀하신 AI활용 방법이었는데, 이번 오류를 찾은 방법이 정확히 그 기준이었다. AI가 구현을 대신 써 주는 만큼, 사람이 할 일은 기대값을 정하는 것과 바뀐 코드를 읽어서 이해하는 것으로 옮겨간다. 둘 중 하나라도 놓으면 초록불만 보고 가게 된다.
