명명은 소프트웨어 개발에서 매우 중요하다. 코드의 가독성, 이해성, 유지보수성에 직접적인 영향을 미치기 때문이다.

### 약어 확장하기

문제 : 모호하게 축약된 이름이 있다.

→ 충분히 길며 모호하지 않고 설명이 포함된 명확한 이름 사용하기

```javascript
package main

import "fmt"

type YVC struct {
   id int
}

func main() {
    fmt.Println("Hello, World")
}
```

예) 수정버전

```javascript
package main

import "formatter"

type YoutTubeVideoContent struct {
    imdbMovieIdentifier int
}

function main() {
    formatter.Printline("Hello, World")
}
```

모델에서 축약되고 모호한 이름은 하나 이상의 가능한 개념에 매핑된다. → 다른 의미로 착각할 수 있고, 의미를 파악하는데 많은 에너지를 낭비할 수 있다.

### 7.2 도우미와 유틸리티 이름 변경 및 분리하기

문제 : Helper라는 이름을 가진 클래스가 있지만 일관성이 없고 동작이 불분명하다.

→ 클래스의 이름을 더 정확안 이름으로 변경하고 책임을 세분화하기

예) 부족한 책임 분담

```javascript
export default class UserHelpers {
	static getFullName(user) {
		return `${user.firstName} ${user.lastName}`;
	}
	
	static getCategory(userPoints) {
		return userPoints > 70 ? 'A' : 'B';
	}
}

import UserHelpers from './UserHelpers';

const alice = {
  firstName: 'Alice',
  lastName: 'Gray',
  points: 78,
};

const fullName = UserHelpers.getFullName(alice);
const category = UserHelpers.getCategory(alice);
```

1. 단일 책임 원칙 (SRP) 준수

*❌ 이전: 하나의 클래스가 여러 책임*

```
UserHelpers {
  - 이름 포맷팅
  - 카테고리 계산
  - 앞으로 추가될 더 많은 기능들...
}
```

1. 명확한 의도 전달

- `UserHelpers` - 무엇을 도와주는 건지 불분명

예) 개선된 코드

```javascript
class UserScore {
  // 이는 빈약한 클래스로 더 나은 프로토콜이 있어야 합니다.

  constructor(name, lastname, points) {
    this._name = name;
    this._lastname = lastname;
    this._points = points;
  }
  name() {
    return this._name;
  }
  lastname() {
    return this._lastname;
  }
  points() {
    return this._points;
  }
}

class FullNameFormatter {      
  fullname(userscore) {
    return `${userscore.name()} ${userscore.lastname()}`;
  }
}

class CategoryCalculator {
  display(userscore) {
    return userscore.points() > 70 ? 'A' : 'B';
  }
}  
  
let alice = new UserScore('Alice', 'Gray', 78);

const fullName = new FullNameFormatter().fullname(alice);
const category = new CategoryCalculator().display(alice);
```

1. 확장성 향상

*// 새로운 포맷이 필요하면 클래스로 추가 (UserHelper에 추가 하지 않음)*

```
class EmailFormatter {
  format(userscore) {
    return `${userscore.name().toLowerCase()}@company.com`;
  }
}
```

### my-객체 이름 변경하기

문제 : 접두사 my가 포함된 변수가 있다.

→ 접두사 my가 포함된 변수의 이름을 변경한다. (해당 객체는 컨텍스트가 부족하고 전단사에 위배된다.)

### result변수 이름 변경하기

문제 : 함수, 메서드 호출 또는 계산의 결과를 result라는 모호한 이름으로 지정한다

→ 항상 역할을 암시하는 좋은 이름을 사용하세요. result는 항상 나쁜 선택이다.

예) 변경 전

```javascript
var result;

result = lastBlockchainBlock();

// 많은 함수가 addBlockAfter(result)를 호출합니다.

addBlockAfter(result);
```

예) 변경 후

```javascript
var lastBlockchainBlock;

lastBlockchainBlock = findlastBlockchainBlock();

// 많은 함수 호출이 있습니다.
// 이들을 리팩터링해 변수 정의와 실제 사용할 때의 공간 간극을 최소화하세요.

addBlockAfter(lastBlockchainBlock);
```

### 타입이 포함된 변수 이름 변경하기

문제 : 타입이 포함된 이름이 있지만 이름은 항상 역할을 나타내야 한다.

→ 타입 제거하기. 타입은 우발적으로 생성도니 것이며 전단사에 존재하지 않는다.

예) 개선 전

```javascript
public bool CheckIfStringHas3To7LowercaseCharsFollowedBy3or4Numbers
    (string textToCheck)
{
        Regex regex = new Regex(@"[a-z]{2,7}[1-9]{3,4}")
        var bool = regex.IsMatch(textToCheck);
        return bool;
}
```

예) 개선 후

```javascript
public bool CheckIfStringHas3To7LowercaseCharsFollowedBy3or4Numbers
    (string password)
{
  Regex stringHas3To7LowercaseCharsFollowedBy3or4Numbers = 
    new Regex(@"[a-z]{2,7}[1-9]{3,4}")
  var hasMatch =
    stringHas3To7LowercaseCharsFollowedBy3or4Numbers.IsMatch(password);
  return hasMatch;  
}
```

### 긴 이름 변경하기

문제 : 매우 길고 중복되는 이름이 있다.

→ 이름은 설명을 하되 너무 길지 않아야 한다. 이름을 줄이되 사용자가 임의로 지정한 약어를 사용하지 말아야 한다.

### 추상적인 이름 변경하기

문제 : 이름이 너무 추상적이다.

→ 실제 MAPPER를 사용해 추상적인 이름을 구체적인 이름으로 변경하기

예) LogCollector, NotesArray, AccountsComposite, MeetingsCollection

### 맞춤법 오류 수정하기

문제 : 이름에 오타 및 철자 실수가 있다.

→ 이름 잘 관리하기

### 속성에서 클래스명 제거하기

문제 : 클래스 명이 포함된 변수가 있다.

→ 속성에 클래스명을 접두사로 붙이지 말기

```javascript
public class Employee {
   String empName = "John";
   int empId = 5; // -> int id; (id는 코드 스멜의 한 종류이다.)
   int empAge = 32; // -> int age; (age도 또한 코드 스멜의 한 종류이다.)
}
```

### 클래스와 인터페이스에서 첫 글자 제거하기

문제 : 클래스의 접두사에 추상, 인터페이스 등을 나타내는 문자를 사용한다.

→ 클래스에 접두사나 접미사 붙이지 말기. 항상 MAPPER 개념 기반으로 완전하고 현실적인 개념 사용하기

```javascript
public interface IEngine // -> Engine로 바꾸기
{
    void Start();
}

public class ACar {} // -> Car로 바꾸기    
```

### basic/do 함수 이름 바꾸기 [다시보기]

문제 : sort, doSort, basicSort, doBasicSort 와 같은 동일한 동작을 표현하는 변형이 많이 존재한다.

→ 함수 래퍼는 혼란을 초래하므로 제거하기

### 복수형 클래스를 단수로 변환하기

문제 : 복수 용어를 사용하는 클래스 이름이 있다.

→ 단수로 변경하기, 클래스는 개념을 나타내고, 개념은 단수이다.

### 이름에서 Collection 제거하기

문제 : 이름에 Collection이 포함되어 있다.

→ 이름에 Collection을 사용하지 않기, 구체적인 개념을 표현하기에는 너무 추상적이다.

```javascript
for (var customer in customerCollection) { // customerCollection -> customers로 변경
	// action
}

for (var customer in customers) {
	// action
}
```

### 클래스 이름에서 Impl 접두사/접미사 제거하기

문제 : Impl 접두사/접미사가 포함된 클래스가 있다.

→ 실제 개념의 이름을 따서 클래스 이름을 짓기.

참고) 인터페이스에 I를 추가하거나 Impl을 추가하지 않도록 주의하기!

### 역할에 따라 인수 이름 변경하기

문제 : 선언적 이름이 아닌 메서드 인수가 있다.

→ 인수 이름을 역할에 따라 지정하기

예) 좋지 않은 예시

```python
class Calculator: 
	def substract(self, first, second):
		return first - second
```

변경

```python
class Calculator:
	def subtract(self, minuend, subtrahend):
		return minuend - subtrahend
```

### 중복된 매개변수 이름 제거하기

문제 : 메서드의 인수 이름이 반복된다.

→ 메개변수 이름을 반복하지 말기, 이름은 문맥에 맞고 지역적이여야 한다.

예)

```ruby
class Emplopyee
	def initialize(
		@employee_first_name : String,
		@employee_last_name : String,
		@employee_birthdate : Time,
	)
	end
end
```

```ruby
class Employee
	def initialize(
		@first_name : String,
		@last_name : String,
		@birthdate : Time,
	)
	end
end
```

### 이름에서 불필요한 컨텍스트 제거하기

문제 : 클래스에 전역 식별자를 접두사 또는 접미사로 사용한다.

→ 이름에 관련 없는 정보를 접두사나 접미사로 붙이지 말기. MAPPER개념을 따르기 위해 이 정보를 제거하고 코드 검색이 수월하도록 하기

```rust
struct WEBBExplanet { // WEBBExplanet -> Explanet
	name : String,
	mass : f64
}

struct WEBBGalaxy { // WEBBGalaxy -> Galaxy
	name : String,
	distance : f64
}
```

### data 명칭 피하기

엔티티 도메인 이름을 사용해 엔티티 도메인 객체를 모델링한다.

→ 변수 이름을 data로 지정하기 말기

```javascript
if (!dateExists()) {
	return 'Loading Data'; 
}
```

수정

```javascript
if (!peopleFound()) {
	return 'loading People';
}
```
