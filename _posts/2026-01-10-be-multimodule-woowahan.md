### 문제: Common 모듈의 저주

처음에는 "공통 코드를 모아서 쓰자"는 단순한 생각으로 **common 모듈**을 만들었는데, 세 가지 문제가 발생했습니다.

1. **스파게티 코드** — 모든 코드가 common에 쌓이면서 하나만 수정해도 전체 시스템에 영향
2. **의존성 덩어리** — DB 안 쓰는 앱도 DB 의존성을 갖게 되고, 불필요한 AutoConfiguration이 작동
3. **공통 설정 문제** — 커넥션 풀 등 앱마다 달라야 할 설정이 하나로 통일되어 장애 유발

### 해결: 5개 계층으로 모듈 분리

모듈을 **역할과 책임**에 따라 계층화했습니다.

| 계층 | 역할 | 예시 |
| --- | --- | --- |
| **독립 모듈** | 시스템과 무관한 라이브러리 | yaml-importer, data-dynamo-reactive |
| **공통 모듈** | 순수 Java만 (Type, Util) | 의존성 없음, 최소한만 사용 |
| **도메인 모듈** | 중심 도메인 + 저장소 | 인프라당 1개 모듈, 서비스 비즈니스 모름 |
| **내부 모듈** | 시스템 서포트 기능 | core-web, xxx-client, event-publisher |
| **어플리케이션 모듈** | 실행 가능한 앱 | app-batch, app-api 등 |

### 핵심 원칙

- **도메인 모듈은 인프라 1개만** — RDBMS 모듈에 Redis 추가하면 의존성 지옥
- **implementation으로 하위 의존 숨기기** — 보호받아야 할 모듈 접근 차단
- **모듈마다 README 필수** — 역할, 사용법, 관례 문서화
- **@ConditionalOnMissingBean** 활용 — 상위 모듈에서 확장/변경 가능하도록 여지 개방

### 효과

- 추상화 경계가 명확해져서 리팩토링 영향 범위 파악이 쉬워짐
- 각 모듈이 필요한 의존성만 가져서 최적화된 실행 환경
- 개발자가 "어디에 뭘 작성해야 하는지" 확신을 갖고 개발 가능
