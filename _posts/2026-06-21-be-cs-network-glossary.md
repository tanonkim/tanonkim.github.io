## 1. 네트워크 토대

### VPC(**Virtual Private Cloud**)

**AWS안에 만드는 격리된 나만의 가상 네트워크**, (클라우드 위에 빌린 전용 데이터 센터)

EC2, RDS, MSK 등 모든 리소스가 이 안에 들어감.

사용이유 : 리소스를 외부와 격리 + IP대역, 라우팅, 방화벽을 내가 직접 통제하기 위함

VPC가 없으면 모든게 인터넷에 그대로 노출된다.

### CIDR

**IP주소를 적는 표기법**

10.xx.xx.xx/16에서 16 : 앞 16비트는 고정, 뒤 16비트는 자유 → 2^16승 : 6만 5천개

**숫자가 작을수록 큰 네트워크**

VPC를 만들 때 전체 IP대역을 이 CIDR로 정한다

### 서브네팅

**VPC의 큰 CIDR을 작은 조각(서브넷)으로 쪼개는 것**

예) 10.xx.xx.xx/16 → 10.xx.xx.xx/24(퍼블릭), 10.xx.xx.xx/24(프라이빗)

- 왜 필요한가
  1. 퍼블릭/프라이빗으로 분리하기 위함
  2. AZ별 분산으로 장애 대비
  3. 보안 경계를 나누기 위해서

서브넷은 AZ개에만 존재한다 → 다중 AZ를 사용하려면 서브넷을 AZ마다 만들기

### RT (Route Table)

(Public RT가 0.0.0.0/0 → IGW를 가질 때 양방향 인터넷이 열린다.)

모든 VPC에는 눈에 안보이는 암묵적 라우터(implicit router)가 내장<br>**RT는 그 라우터에게 주는 길 안내 규칙표**

RT = 라우팅 규칙(목적지가 X이면 타겟 Y로 보내라)<br>실제 패킷을 옮기는 건 VPC 내장 라우터

결론 : RT가 라우팅을 결정한다.

- Public RT : 0.0.0.0/0 0 → IGW ⇒ 그 서브넷은 퍼블릭이 됨
- Private RT : 0.0.0.0/0 → NAT GW (나가기만 가능)

> IGW 경로가 있으면 외부와 직접 소통하는 경로가 생긴다<br>외부에서 들어오려면 그 리소스에 공인 IP + 방화벽(**SG/NACL**(Network ACL))이 허용되어야 한다<br>RT + 공인IP + 방화벽(SG/NACL)

## 2. 인터넷 연결과 egress

### IGW (Internet Gateway)

**VPC와 인터넷을 잇는 정문**

Public RT가 IGW를 가르켜야 서브넷이 퍼블릭이 된다.

### NAT / NAT Gateway / NAT egress

**프라이빗 서브넷**의 리소스가 **나가기만** 할 수 있게 도와주는 장치

egress : 아웃바운드(나가는) 트래픽

Private EC2도 외부 API 호출 or OS 다운로드 등등 해야 하지만, 외부가 먼저 들어오는건 막고 싶을 때 NAT 사용

**NAT은 퍼블릭 서브넷에 위치한다**

> 흐름 : Private EC2 → Private RT(0.0.0.0/0 → NAT) → NAT GW(퍼블릭 서브넷) → IGW → 인터넷<br>외부가 먼저 EC2로 연결하는건 불가능 (NAT이 보안에 기여하는 핵심)

### EIP (Elastic IP)

고정 IP

NAT GW에 붙여서 아웃바운드 트래픽의 출발 IP를 고정

필요이유 : 외부 파트너 등이 이 IP만 허용(IP 화이트리스트)를 요구하거나, IP가 바뀌면 안되는 등

### Bastion

브라이빗 리소스에 SSH로 접속하기 위한 징검다리 서버

퍼블릭 서브넷에 두고, 관리자가 Bastion에 먼저 접속한 후 거기서 Private으로 들어감.

단점 : 22번 포트 노출 + 서버관리 부담 → 요즘은 SSM으로 대체

필요시 사용

## 3. 접근과 보안

### SSM(System Manager / Session Manager)

Bastion 없이 SSH, 22번 포트, 공인IP없이 프라이빗 EC2셸에 접근하는 현대적인 방법

EC2에 설치된 SSM 에이전트가 SSM 서비스로 아웃바운드 연결을 맺어둠, 관리자는 AWS 콘솔/CLI로 그 통로로 접근 (인바운드 포트를 하나도 안열어도 됨)

### NACL (Network ACL)

**서브넷 경계의 방화벽**

서브넷을 드나드는 트래픽을 IP/포트 단위로 허용 or 차단

SG가 인스턴스 한 대 단위라면 NACL은 서브넷 전체에 한 겹 더 두르는 방어막

- NACL에서 Stateless하다는 의미는?

  연결 상태를 기억하지 않는다.

  들어온 패킷과 나가는 패킷을 따로 심사한다. → 인바운드 443을 허용해도, 그 응답이 나갈 때 쓰는 아웃바운드 규칙을 별도로 허용해야 한다.

  ↔ SG는 Stateful : 인바운드를 허용하면 그에 대한 응답, 아웃바운드는 자동 허용(기억을 한다)

  - SG는 왕복 한 번에 처리, NACL은 올때/갈때 따로 허용

### ephemeral 포트 (어페머럴)

**임시 포트**

클라이언트가 서버(443)에 접근할 때 임시로 높은 번호 포트를 출발 포트로 쓴다. 예) 34521

서버응답은 이 임시포트로 돌아오는데 NACL은 stateless라서 이 응답 트래픽을 명시로 허용해야 한다.

⇒ NACL규칙에 1024-65535같은 ephemeral 포트를 연다. (**Stateless라서!**)

## 4. 애플리케이션 계층

### ALB (Internal, External 차이점)

HTTP/HTTPS(L7)로드밸런서

트래픽을 분산, 경로별 라우팅을 한다. (api, img 등)

|  | **External ALB** | **Internal ALB** |
| --- | --- | --- |
| IP | 공인 IP 보유 | 사설 IP만 |
| 위치 | 퍼블릭 서브넷 | 프라이빗 서브넷 |
| 접근 주체 | 인터넷의 외부 사용자 | **VPC 내부 서비스끼리** |
| 용도 | 서비스의 외부 진입점 | **마이크로서비스 내부 통신** |

### ASG (AutoScaling Group)

EC2 인스턴스 대수를 자동으로 관리

1. 원하는 대수 유지
2. 죽은 인스턴스 교체
3. 부하에 따라 자동 증감

ALB와 짝궁

왜 필요한가 : 가용성/탄력성, 비용최적화

### Amazon MSK (Managed Streaming for Apache Kafka)

AWS가 관리해주는 완전 관리형 Kafka

Kafka는 대용량 이벤트/메시지 스트리밍 플랫폼, 서비스 간 비동기 통신/로그 수집/실시간 데이터 파이프라인에 사용한다.

**보통 프라이빗 서브넷에 둔다.**

## 5. 이 모든걸 만드는 도구

### Terraform

위의 VPC·서브넷·NAT·ALB·ASG·MSK 전부를 **콘솔에서 클릭하는 대신 코드로(IaC, Infrastructure as Code)** 정의하는 도구

HCL이라는 설정 파일에 "이런 인프라를 원한다"고 선언하면 Terraform이 생성·변경·삭제를 자동으로 수행한다.

**_왜 필요한가:_ 버전 관리(Git), 재현성(dev/stg/prod 동일 구성), 코드 리뷰, 실수 방지. 즉 이 목록 전체를 실제로 구축하는 수단입니다.**
