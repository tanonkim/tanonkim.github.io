## 왜 캐시를 붙였나

고객 상품 목록 `GET /api/v1/products?brandId=&sort=&page=&size=`에는 정렬이 세 가지 있다. 인덱스와 쿼리 분리를 마친 뒤 seed 1만 개에서 재 보니 좋아요순이 HTTP p50 약 24 ms였다(아래 표를 만들며 같은 1만 개를 다시 잰 값은 31.5 ms).

24 ms면 빠르다. 캐시를 붙일 이유가 되나? 1만 개에서는 판단할 수 없어서, 같은 seed 규칙으로 상품을 10만·100만·500만 개까지 늘려 다시 쟀다.

- 측정: 매 회 세대를 올려(쓰기 직후와 같은 상태) 원본 조회(miss) 1번, 같은 요청을 다시 보내 hit 1번. 두 응답의 `data`가 같은지 함께 확인했다. 1만·10만은 30회, 100만은 20회, 500만은 10회. 첫 페이지 20개.

| 조회 (HTTP p50, ms) | 1만 | 10만 | 100만 | 500만 | hit (1만 → 500만) |
|---|---|---|---|---|---|
| 전체 · 좋아요순 | 31.5 | 212.6 | 2,243 | **11,364** | 5.7 → 9.3 |
| 브랜드 · 좋아요순 | 12.0 | 18.7 | 134.6 | 637.2 | 5.9 → 8.9 |
| 전체 · 가격순 | 15.5 | 35.7 | 328.1 | 1,595 | 5.5 → 8.3 |
| 브랜드 · 가격순 | 11.0 | 11.7 | 14.1 | **17.9** | 5.1 → 5.6 |
| 전체 · 최신순 | 14.2 | 18.0 | 81.1 | 441.2 | 6.0 → 7.6 |

표가 두 무리로 갈린다.

- **인덱스로 읽는 양을 묶은 조회는 규모와 상관없다.** 브랜드 가격순은 상품이 500배가 되어도 11 → 18 ms다. `(brand_id, deleted_at, price, id DESC)` 구간을 앞에서 20개만 읽기 때문이다. 이 조회에 캐시는 필요 없다.
- **인덱스로 줄일 수 없는 조회는 데이터에 비례해 커진다.** 전체 좋아요순은 상품 전부의 좋아요를 세야 순서가 정해진다. 500만 개에서 11초다. 브랜드 필터가 없는 가격순은 쓸 인덱스가 없어 전체를 정렬한다.
- **최신순에 숨은 비용이 있었다.** 내용 20개는 PK 역순으로 읽어 0.07 ms면 끝난다. 그런데 응답에 전체 건수가 들어가서, `count(*)`가 삭제되지 않은 상품 495만 개를 전부 센다(500만에서 `EXPLAIN ANALYZE` 671 ms). 정렬이 아니라 페이지 정보가 비쌌다.

hit은 어느 규모에서나 5~9 ms다. 캐시가 의미 있는 곳은 1만 개의 좋아요순(24 ms)이 아니라, **데이터가 늘수록 함께 커지는 조회**였다. 1만 개에서 캐시를 붙인 판단은 맞았지만, 근거는 "지금 느리다"가 아니라 "데이터에 비례해 느려진다"여야 했다.

참고로 hit 5 ms 중 Redis 몫은 작다. Redis GET 왕복 p50 133 µs, JSON 역직렬화 p50 9.7 µs(목록 20개, 2.6 KB)였다.

## 순진하게 캐시 붙이기

흔히 보는 cache-aside 그대로 만들었다.

- 조회: 캐시를 본다 → 없으면 DB에서 읽는다 → 캐시에 넣는다(TTL 60초).
- 쓰기: 트랜잭션 안에서 DB를 고치고, 목록 캐시를 지운다.

한 번에 한 요청씩 보내는 테스트는 모두 통과했다. miss와 hit의 결과가 같고, 가격을 바꾸면 다음 조회에 새 가격이 보였다.

## 실패 장면을 만들었더니 6개가 모두 실패했다

문제는 요청이 엇갈릴 때만 드러난다. 실제로는 드물어서 그냥 돌려서는 재현되지 않는다. 그래서 테스트 전용 데코레이터(`ControllableProductListCache`)로 실제 Redis 캐시를 감싸, "무효화 직후에 멈춰라", "저장 직전에 멈춰라", "무효화를 실패시켜라"를 걸어 순서를 고정했다. Redis 장애는 테스트 전용 Redis 컨테이너를 실제로 멈췄다.

| 장면 | 기대 | 실제 |
|---|---|---|
| ① 가격 변경 rollback | 1,000 | 9,000 |
| ② 무효화와 commit 사이에 들어온 조회 | 3,000 | 1,000 |
| ③ 늦은 채움 | 3,000 | 1,000 |
| ④ commit 뒤 무효화 실패 | 변경 성공 | 변경까지 실패 (`RedisConnectionFailureException`) |
| ⑤ 무효화 실패 + 상품 삭제 | 삭제 성공, 삭제 상품 비노출 | 삭제까지 실패 |
| ⑥ Redis 중단 | 짧게 기다리고 DB 결과 | 3초 안에 응답 없음 |

**Redis는 DB 트랜잭션에 묶이지 않는다.** DB가 rollback해도 Redis에 쓴 것은 남고, DB가 commit하기 전이라도 Redis를 지운 것은 다른 요청에 바로 보인다.

②를 시간 순서로 보면 이렇다.

```
관리자:  가격 3,000 → 캐시 지움 → (commit 전) ─────────────→ commit
고객:                         캐시 없음 → DB 읽음(아직 1,000) → 캐시에 1,000 저장
```

지운 자리를 옛 값이 다시 채웠다. 그럼 commit 뒤에 지우면 될까? ③이 그 답이다.

```
고객:    캐시 없음 → DB 읽음(1,000) → (저장 직전) ────────────────→ 캐시에 1,000 저장
관리자:                       가격 3,000 → commit → 캐시 지움(지울 것 없음)
```

먼저 읽은 조회가 지운 **뒤에** 옛 값을 써 넣는다. 지우는 시점을 아무리 옮겨도, 옛 값이 다시 들어갈 틈은 남는다.

## 하나씩 고쳤고, 고칠 때마다 비용이 생겼다

| 장면 | 고친 방법 | 얻은 것 | 낸 것 |
|---|---|---|---|
| ① | 쓰기 트랜잭션 안의 조회는 캐시를 거치지 않는다 | commit 안 된 값이 캐시에 들어가지 않음 | — |
| ② ④ ⑤ | 무효화를 commit **뒤**로 옮기고, 실패해도 로그만 남긴다 | 지운 자리를 옛 값이 채우지 못함. 캐시 오류가 관리자 변경을 실패시키지 않음 | Redis가 느리면 쓰기마다 DB 커넥션을 최대 200 ms 더 쥔다. 무효화가 실패하면 TTL(60초) 동안 옛 값이 보인다 |
| ③ | 키에 **세대 번호**를 넣는다. 조회는 DB를 읽기 전에 세대를 읽고, 쓰기는 commit 뒤 세대를 올린다 | 늦게 저장한 값은 옛 세대 키에 들어가 아무도 읽지 않음 | 조회마다 Redis 왕복 2번. **어떤 쓰기든 목록 캐시 전체가 무효화된다** |
| ⑤ | hit여도 담긴 상품이 아직 팔 수 있는지 PK `IN`으로 확인한다 | 무효화가 실패해도 삭제 상품은 보이지 않음 | hit에도 SQL 1개가 남는다 |
| ⑥ | Redis 명령·연결 대기를 200 ms로 묶고, 실패하면 DB에서 읽는다 | Redis가 죽어도 목록이 나옴. 다시 뜨면 캐시가 다시 채워짐 | 최악의 경우 한 요청이 약 1초 기다린다. 이 상한은 Redis 모듈을 쓰는 다른 앱에도 걸린다 |

③에서 다른 방법도 봤다.

- **지연 이중 삭제**(commit 뒤 지우고, 예를 들어 500 ms 뒤 한 번 더 지우기): 늦게 들어온 옛 값을 두 번째 삭제가 치워 준다. 하지만 옛 값의 저장이 두 번째 삭제보다도 늦으면(GC나 네트워크 지연으로 2초 멈춘 조회) 그대로 남는다. 문제가 생기는 경우를 드물게 만들 뿐 없애지 못하고, 대기를 늘릴수록 옛 값을 보는 시간도 길어진다. 세대 번호는 저장이 얼마나 늦든 옛 세대 키에 들어가므로 이 조건이 없다.
- **DB에 revision 행을 두고 hit마다 확인**: 권위 있는 버전이지만, 모든 쓰기가 같은 행을 갱신해 핫 로우가 된다. 좋아요가 그 행의 잠금에 줄을 선다.

## 그래서 나는 무엇을 골랐나

- **(처음 선택) 옛 가격은 TTL 안에서 허용, 삭제 상품 노출은 허용하지 않는다.** 둘 다 "캐시가 원본과 다르다"지만 무게가 다르다. 60초 늦은 가격은 결제 금액에 영향을 주지 않는다(주문은 원본 가격으로 계산한다). 하지만 삭제된 상품이 보이면, 고객은 고른 상품을 주문하는 순간 "상품을 찾을 수 없습니다"를 받는다. 목록이 존재하지 않는 상품을 약속한 셈이다. 그래서 hit에도 SQL 1개를 남기는 비용을 냈다.
- **캐시는 보조다.** 캐시가 실패하면 원본으로 돌아가고, 쓰기를 실패시키지 않는다. 반대로 DB 오류는 캐시 값으로 덮지 않는다.
- **정확성을 hit율보다 먼저 둔다.** 세대 하나로 전체를 무효화하는 건 거칠다. 하지만 상품 하나가 어느 목록 키의 어느 페이지에 섞여 있는지 따라가는 것보다 단순하고, 늦은 채움까지 막는다.

## 멘토링 뒤 한 번 더 바꿨다: 목록과 상품 값을 나눈다

멘토님께 "넓게 캐시했다면 수정은 어떻게 반영하나"를 여쭸더니, 목록과 상품을 나누라는 답을 들었다. 목록에는 순서 같은 메타데이터를 두고, 가격·재고처럼 틀리면 안 되는 값은 id로 원본을 확인하라는 것이다. 목록 순서가 1분쯤 어긋나는 건 큰 문제가 아니고, 뒤 페이지는 hit율이 낮으니 앞쪽만 캐시하라는 말씀도 있었다.

돌아보니 절반은 이미 하고 있었다. ⑤를 막으려고 hit 때마다 PK `IN`으로 "아직 팔 수 있는가"를 확인하고 있었기 때문이다. 이 쿼리가 id 대신 상품 행을 읽게만 바꾸면, SQL 개수는 그대로 1개인데 이름·가격을 원본 값으로 덮을 수 있다.

| | 캐시가 맡는다 (TTL 안에서 어긋나도 됨) | 원본이 맡는다 (어긋나면 안 됨) |
|---|---|---|
| 전 | 순서·건수·좋아요 수·이름·가격 | 판매 가능 여부 |
| 후 | 순서·건수·좋아요 수·브랜드 이름 | 판매 가능 여부·**이름·가격** |

그래서 ④의 테스트 기대를 바꿨다. 전에는 "무효화가 실패하면 TTL 동안 옛 가격이 보인다"를 허용했고, 이제는 "가격은 바로 원본 값이고, 가격순의 순서만 TTL 동안 옛 순서일 수 있다"를 확인한다. 기대를 느슨하게 한 게 아니라 강하게 한 쪽이다. PK 20건 조회는 규모 측정에서 본 브랜드 가격순처럼 데이터가 늘어도 비용이 그대로라, 이 강화는 거의 공짜였다.

캐시도 앞 3페이지(page 0~2)만 하기로 했다. 뒤 페이지는 hit율이 낮은데 캐시하면 키 조합만 늘어난다.

## 아직 못 정한 것, 주장하지 않는 것

- **좋아요 한 번에도 목록 캐시 전체가 무효화된다.** 정확성 문제는 아니고 hit율 비용이다. 규모 측정으로 보면, 브랜드 가격순처럼 인덱스로 묶인 조회는 캐시하지 않아도 된다. 데이터에 비례하는 조회(전체 좋아요순·전체 가격순·전체 건수)만 캐시하고, 그중 좋아요순은 무효화 대신 주기 갱신으로 바꾸는 방법을 생각하고 있다. 이름·가격이 hit에서도 원본이 된 지금은, 상품 수정이 목록을 아예 무효화하지 않고 가격순의 순서만 TTL에 맡기는 것도 가능해졌다. "쓰기를 목록에 모두 반영한다"는 기준과 어떻게 맞출지 아직 정하지 않았다. 부하에서 hit율을 재 본 뒤 정하려 한다.
- 전체 건수 `count(*)`는 캐시가 아니어도 줄일 수 있다(건수를 따로 유지하거나, "다음 페이지 있음"만 알려 주기). 이번에는 다루지 않았다.
- 지연은 로컬 단일 머신에서 순차 요청으로 쟀다. 10 ms 안팎의 차이는 실행마다 흔들려서 결론으로 쓰지 않았고, 규모에 따라 몇 배·몇십 배로 벌어지는 차이만 썼다.
- 동시 부하에서의 hit율, 처리량, DB CPU, replica 지연은 재지 않았다.

## 배운 것

캐시가 필요한지는 지금 몇 ms인지가 아니라, 데이터가 늘 때 함께 커지는 조회인지로 정해야 했다. 1만 개만 봤다면 "24 ms인데 굳이?"에서 멈췄을 것이다.

캐시를 붙이는 코드는 짧다. 틀리지 않게 만드는 일은 "캐시가 원본과 달라도 되는 경우와 안 되는 경우"를 정하는 일이었다. 그리고 그 경계는 순서를 고정한 실패 테스트가 없었다면 보이지 않았다.
