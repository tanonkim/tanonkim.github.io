## **요청사항**

알림톡/sms/email관련한 요청들이 많아지기 시작함

현재 as-is(한 프로젝트에서 다 실행중임)의 문제점을 정리하고, to-be 어떤 방식으로 하는게 좋을지 아키텍쳐를 설계하고 구현에 대한 구체적인 플랜을 작성

### 제약사항 :

알림톡, sms은 외부 서비스이고, 언제든지 장애가 날 수 있다. 적어도 3개 이상의 프로젝트에서 각자 sms, 알림톡을 보내고 있다. 꼭 필수적으로 나가야 할 메세지가 있고, 아닌 메세지가 있다. 비용 절감도 필요하다. 앞으로 확장가능성을 고려해서 설계가 되어야 한다. 100개 이상의 서비스가 요청을 할 수 있다.

## 해결

알림톡/SMS/Email 발송 수요가 계속 증가하고, 향후 100개 이상의 서비스가 요청할 수 있는 구조를 고려하면, 개별 서비스가 직접 발송 로직을 가지는 방식보다 **중앙 Notification Platform** 형태로 구성하는 것이 적절 (Message 서버)

- 구현 방향
  - **API + JMS + Message Broker + Channel Worker** 구조.
  - 각 서비스가 직접 SMS/Email/알림톡 등 벤더 호출 → Notification API 호출
  - 이 API는 발송 요청을 검증하고 바로 외부 벤더 호출하는게 아닌, JMS 기반 비동기 처리구조로 브로커에 적재
  - 브로커 : ActiveMQ를 우선 활용
  - 이유 : JMS 표준 기반으로 Producer/Consumer 구조를 단순하게 가져갈 수 있고, 비동기처리/재처리 구조/서비스 간 느슨한 구조를 구성할 수 있음

### 1. 모든 서비스의 발송 요청은 단일 진입점으로 받기

각 서비스가 개별적으로 SMS/알림톡/Email 벤더를 직접 호출하는 구조가 아니라,

모든 서비스는 **Notification Gateway API** 또는 경량 SDK를 통해 발송 요청을 보내도록 구성.

이렇게 하면

- 서비스마다 발송 로직이 중복되지 않고
- 정책 변경 시 중앙에서 관리할 수 있으며
- 신규 서비스가 늘어나도 동일한 방식으로 쉽게 연동할 수 있습니다.

### 2. 내부적으로는 채널별 Worker 분리

플랫폼 내부는 하나의 서버에서 전부 처리하기보다, 다음처럼 **채널별로 독립된 Worker**로 분리

- SMS Worker
- 알림톡 Worker
- Email Worker

이 구조를 사용하면 특정 외부 서비스 장애가 발생해도 다른 채널로 영향이 번지는 것을 최소화할 수 있고, 채널별로 독립적인 확장도 가능

### 3. 메시지는 우선순위 기반으로 처리

모든 메시지를 동일하게 처리하지 않고, 비즈니스 중요도 기준으로 최소한 아래처럼 구분

- **Critical**: 인증번호, 결제완료, 보안 알림 등 반드시 나가야 하는 메시지
- **High**: 회원가입, 문의 답변, 주요 운영 알림
- **Normal**: 일반 안내성 메시지
- **Low**: 마케팅, 리마인드, 비필수 안내

이 우선순위를 기준으로 큐와 소비 정책을 분리하면, 트래픽이 몰리는 상황에서도 중요한 메시지를 먼저 안정적으로 처리할 수 있다.

### 4. 필수 메시지는 Fallback 정책 내장

알림톡과 SMS는 외부 서비스 의존성이 높기 때문에,

“꼭 나가야 하는 메시지”에 대해서는 플랫폼 레벨에서 fallback 정책을 둔다.

예를 들어

- 알림톡 실패 시 SMS fallback
- Email 실패 시 재시도 후 운영 알림
- 특정 벤더 장애 시 대체 벤더 전환 가능 구조

처럼 설계하면 서비스마다 예외처리를 중복 구현하지 않아도 된다.

### 5. 비용 최적화는 플랫폼에서 통합 관리

비용 절감을 위해서는 단순 발송 기능보다 **정책 기반 운영**

예를 들어

- 가능하면 알림톡 우선 발송
- 실패 시에만 SMS fallback
  - 알림톡 실패 → SMS fallback
  - SMS 일시 실패 → 재시도
  - 최종 실패 → `DLQ` 적재 후 운영 알림
- 중복 발송 방지
- 비필수 메시지는 배치 또는 속도 제한 적용
- 템플릿 통합 관리
- 채널별 성공률/단가/대체발송률 분석

### 6. 운영 관점에서는 통합 로그와 모니터링 필수

플랫폼에는 반드시 아래 정보가 남아야 한다.

- 어떤 서비스가 요청했는지
- 어떤 메시지 유형인지
- 어떤 채널로 발송했는지
- 성공/실패 여부
- 재시도 횟수
- fallback 여부
- 건별 비용
- 외부 벤더 응답 결과

이 데이터가 있어야 장애 대응, SLA 관리, 비용 분석, 정책 개선이 가능합니다.
