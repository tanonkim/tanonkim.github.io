### **1. 왜 VPC/네트워크가 최우선인가**

- 보안
  - 퍼블릭/프라이빗 DB 서브넷을 나누지 않으면 프라이빗 DB가 외부에 노출되는 사고가 난다.
  - 경계가 없으면 SG, NACL로 막을 대상 자체가 모호해진다.
- 비용
  - 트래픽 흐름을 모르면 기준이 안 잡힌다.
  - 어디서 어디로 나가는지 NAT,AZ간 전송이 보여야 무엇을 줄일 지 판단 가능
- 장애 분리/복구
  - AZ, 티어가 분리되어야 한 곳이 죽어도 격리된다.
  - 경계가 없으면 장애가 번지고, 복구가 지연된다.
- 확장 기준
  - 대역(CIDR)과 서브넷이 계획되어있어야 신규 서비스,피어링,Onpremise 연동을 충돌없이 한다.

### 개념들

#### 1. CIDR, Subnet - 가용 IP 수를 정하는 것

서브넷을 나눈다 : 그 서브넷에 들어갈 수 있는 IP의 개수를 정하는 일이다.

| **CIDR** | **총 주소 수 (2의 거듭제곱)** | **AWS 사용 가능 IP** | **쓰임 예** |
|---|---|---|---|
| `/16` | 2^16 = 65,536 | ~65,531 | VPC 전체 대역 |
| `/20` | 2^12 = 4,096 | 4,091 | AZ별 블록(여유) |
| `/24` (C클래스) | 2^8 = 256 | **251** | 티어별 서브넷 |
| `/28` | 2^4 = 16 | 11 | 최소 단위(엔드포인트 등) |

- C클래스에서 일부 빼기 : AWS는 서브넷마다 5개를 예약
  - 네트워크 주소(.0), vpc 라우터 (.1), DNS(.2), 향후 예약(.3), 브로드캐스트(.255)
- 10.x A클래스 남발하지 않는 이유
  - 10.0.0.0/8은 사설 대역 → 아무것도 써도 되나? X
  - 온프레미스, 다른 VPC 피어링 대상과 대역기 겹치면 라우팅이 불가능해진다.(겹친 IP는 어디로 보낼 지 결정할 수 없음)
  - VPC당 리소스 리밋(서브넷, ENI, NAT 수)이 있어 무계획 확장 X
  - VPC가 `10.xx.xx.xx/16`이면 신규는 `10.xx.xx.xx/16`처럼 겹치지 않게 미리 배정.

#### 2. 퍼블릭/프라이빗 DB 서브넷 분리

서브넷의 프라이빗/퍼블릭을 가루는 기준은 라우팅 테이블.

0.0.0.0/0 → IGW 경로가 있으면 퍼블릭, 없으면 프라이빗

- 퍼블릭 서브넷
  - 인터넷에 직접 닿아야 하는 것만
  - ALB, NAT Gateway, Bastion(필요 시)
- 프라이빗-앱 서브넷
  - EC2, 공인 IP 없음
  - 밖으로 나갈 땐 NAT 경유
- 프라이빗-DB 서브넷
  - DB 상태 저장, 앱 서브넷에서만 접근 → 인터넷 경로 없음
  - 사내 : DB는 Onpremise에 있으므로, 이 티어는 Onpremise DB로 가는 사설 게이트웨이 계층이 된다.

#### IGW(인터넷 게이트웨이), NAT Gateway

- IGW 인터넷 게이트웨이 : VPC당 1개
  - 퍼블릭 서브넷의 라우팅 테이블이 0.0.0.0/0 → IGW를 가질 때만 양방향 통신이 열림
- NAT Gateway
  - 프라이빗 서브넷이 밖으로 나갈 때만 쓰는 단방향 출구
  - 정의보다 동작이 중요하다.

**NAT Gateway**

- 들어오는 요청엔 NAT이 불필요
  - 외부가 ALB로 들어와 앱이 응답하는 트래픽은 세션이 유지됨 → 그 경로 그대로 되돌아감
- 앱이 먼저 밖으로 나갈 때 NAT 필요
  - 예) 크롤링, 외부 API 호출
- 같은 IP로 계속 찔러 차단 → NAT교체로 출구 IP변경 가능
  - 고정 egress IP를 가질 때만 가능함
- 포트 고갈 주의
  - NAT 1개에 트래픽이 몰리면 SNAT 포트가 마름
  - AZ별로 NAT를 나눠 분산하고 단일 장애점 삭제

#### **리전 · AZ · ALB**

- **리전**
  - `ap-northeast-2`(서울). 사용자와 가까워 빠르고, **개인정보보호법상 한국 리전**이 안전하다.
- **AZ(가용영역)**
  - 같은 리전 안의 물리적으로 분리된 데이터센터.
  - **2a/2c 등 2개 이상에 분산**해야 한 곳 장애·용량부족에도 견딘다(이중화·고가용성).
- **ALB**
  - **external**(공인 IP, 인터넷 인입용)
  - **internal**(공인 IP 없음, VPC 내부 서비스 간 호출용)을 구분해서 쓴다.

### 4. TO-BE

온프레미스 DB는 그대로 두고, **AWS 쪽 네트워크만 정석 3-tier로** 다시 그리기.

**4.1 대역(CIDR), 서브넷 계획**

기존 `10.xx.xx.xx/16`과 **겹치지 않도록** 신규 VPC를 `10.xx.xx.xx/16`으로 잡는다(피어링 가능 조건). <br>AZ별로 `/20` 블록을 떼고, 그 안에서 티어별 `/24`로 나누기

| **티어** | **AZ ap-northeast-2a** | **AZ ap-northeast-2c** | **사용 IP** | **들어갈 것** |
|---|---|---|---|---|
| **퍼블릭** | `10.xx.xx.xx/24` | `10.xx.xx.xx/24` | 각 251 | External ALB, NAT GW(+EIP) |
| **프라이빗-앱** | `10.xx.xx.xx/24` | `10.xx.xx.xx/24` | 각 251 | EC2 main·admin, Internal ALB |
| **프라이빗-데이터** | `10.xx.xx.xx/24` | `10.xx.xx.xx/24` | 각 251 | VPN GW/Subnet Router, 상태저장 전용노드 |

> 보안상 이미지를 생략했습니다.

**라우팅 테이블 설계**

“퍼블릭/프라이빗”은 결국 라우팅으로 결정됩니다. 티어별 경로를 명시적으로 박기

| **라우팅 테이블** | **대상(destination) → 타깃** | **의미** |
|---|---|---|
| **퍼블릭 RT** | `10.xx.xx.xx/16` → local · `0.0.0.0/0` → IGW | 인터넷 양방향(ALB·NAT만 거주) |
| **앱 RT (2a)** | local · `0.0.0.0/0` → **NAT-a** · 온프렘 → VPN · `10.xx.xx.xx/16` → pcx | 인입 불가, egress는 NAT, DB는 VPN, 기존VPC는 피어링 |
| **앱 RT (2c)** | local · `0.0.0.0/0` → **NAT-c** · 온프렘 → VPN | AZ별 NAT로 포트고갈·장애 격리 |
| **데이터 RT** | local · 온프렘 CIDR → VGW/Router **(인터넷 경로 없음)** | 완전 격리 — 외부로 못 나가고 앱에서만 닿음 |

**접근 제어 — SG 체인 + NACL 이중화**

| **계층** | **Security Group (stateful)** | **NACL (서브넷, stateless)** |
|---|---|---|
| **퍼블릭/ALB** | **alb-sg**: inbound 443 ← `0.0.0.0/0` | 80/443 in, ephemeral out 허용 |
| **앱** | **app-sg**: inbound 앱포트 ← **alb-sg/internal-alb-sg에서만** | 퍼블릭 서브넷 CIDR + ephemeral만 |
| **데이터** | **data-sg**: inbound DB/관리포트 ← **app-sg에서만** | 앱 서브넷 CIDR만 허용, 그 외 deny |
