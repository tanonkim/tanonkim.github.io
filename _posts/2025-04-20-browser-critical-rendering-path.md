중요한 렌더링 경로는 **웹페이지가 브라우저에서 렌더링을 시작**할 때 까지의 단계를 말한다.

페이지를 렌더링하려면 브라우저에 HTML 문서 자체와 이 문서를 렌더링하는데 필요한 중요한 리소스가 필요하다. 페이지를 렌더링하기 위해 HTML 문서를 다운로드 한 후 브라우저가 실행하는 작업에 대해 살펴보자.

## 프로그레시브 렌더링

웹은 본질적으로 **분산**되어있다. 브라우저는 페이지를 렌더링하는데 필요한 모든 리소스가 웹사이트에 있다고 가정할 수 없다. (사용하기전에 설치되는 네이티브 애플리케이션과는 차이가 있다.) 따라서 브라우저는 페이지를 렌더링하는데 능숙하다.

브라우저는 손상된 환경을 보여주지 않기 위해 기다려야 하는 최소 리소스 수를 알아야 한다.

↔ 모든 리소스를 사용할 수 있을 때까지 기다리면 사용자는 오랜 시간을 기다려야 한다.

↔ CSS/JS가 포함되기 전에 HTML이 포함된 상태에서 최대한 빠르게 랜더링을 하면 일시적으로 손상된 것 처럼 보이고, 최종 렌더링 시 상당히 변경된다.

중요한 렌더링 경로를 이해하면 **초기 페이지 렌더링을 필요 이상으로 차단**하지 않아 웹 성능을 개선할 수 있다. 동시에 중요한 렌더링 경로에서 초기 렌더링에 필요한 리소스를 삭제하여 **렌더링이 너무 일찍 발생**하지 않도록 하는 것도 중요하다.

## 중요한 렌더링 경로

[브라우저 구조 부터 DOM과 CSSOM, 렌더링 과정](/posts/browser-structure-dom-cssom-rendering/)

렌더링 경로에는 다음의 단계가 포함된다.

![](/assets/img/2025-04-20/browser-critical-rendering-path-1.png)

- HTML에서 문서 객체 모델(DOM)을 구성한다.
- CSS에서 CSS 객체 객체 모델(CSSOM)을 구성한다.
- DOM 또는 CSSOM을 변경하는 JavaScript를 적용한다.
- DOM 및 CSSOM에서 렌더링 트리 구성
  - DOM 트리와 CSSOM 트리를 합쳐 렌더 트리를 생성한다.
  - 렌더 트리는 실제 화면에 표시될 노드만을 포함한다.
- 페이지에서 스타일 및 레이아웃 작업을 실행하여 어떤 요소가 어디에 적합한지 확인
- 메모리에 있는 픽셀을 **페인트**
- 겹치는 픽셀이 있으면 **합성**
- 결과로 나온 모든 픽셀을 화면에 실제로 그림

렌더링 프로세스는 여러번 실행된다. 초기 렌더링은 이 프로세스를 호출하지만, 페이지 렌더링에 영향을 미치는 리소스가 더 많이 사용가능해지면 브라우저는 이 프로세스 또는 일부만 다시 실행하여 사용자가 보는 내용을 업데이트한다.

### 중요한 렌더링 경로에 있는 리소스

브라우저는 초기 렌더링을 완료하기 전에 일부 중요한 리소스가 다운될 때 까지 기다려야 한다. 다음과 같은 리소스가 포함되어있다.

- HTML의 일부
- `<head>`요소의 렌더링 차단 CSS
- `<head>`요소의 렌더링 차단 JavaScript

브라우저가 HTML을 스트리밍 방식으로 처리한다.

초기 렌더링의 경우 브라우저는 다음을 기다리지 않는다.

- 모든 HTML
- 폰트
- 이미지
- `<head>`요소 외부의 렌더링의 차단하지 않는 JavaScript
  - 예: HTML 끝에 배치된 `<script>`
- `<head>` 요소 외부의 렌더링 차단이 아닌 CSS
- 현재 뷰포트에 적용되지 않는 media 속성 값이 있는 CSS

### `<head>`

`<head>`요소는 중요한 렌더링 경로를 처리하는데 중요하다. `<head>`요소에는 페이지 및 리소스에 관한 메타데이터가 포함되어있지만, 사용자가 볼 수 있는 실제 콘텐츠는 포함되어있지 않다. 표시되는 콘텐츠는 `<head>`요소 뒤에 오는 `<body>`요소 내에 포함된다.

브라우저에서 콘텐츠를 렌더링하려면 **렌더링할 콘텐츠**와 **렌더링 방법에 관한 메타데이터**가 모두 필요한다.

`<head>`요소에 참조하는 모든 리소스가 초기 페이지 렌더링에 꼭 필요한 것은 아니다. 그래서 브라우저는 필요한 리소스를 기다린다. 중요한 렌더링 경로에 있는 리소스를 파악하려면 렌더링 차단 및 파서 차단 CSS 및 JS를 이해해야 한다.

### 렌더링 차단 리소스

일부 리소스는 매우 중요하다고 간주되어 브라우저가 이를 처리할 때 까지 페이지 렌더링을 일시 중지한다.

예) CSS

브라우저가 CSS를 보게 되면 CSS 다운로드 및 다운이 완료될 때 까지 더 이상 콘텐츠를 렌더링하지 않는다.

- 렌더링을 하지 않는다 : 리소스가 렌더링을 차단한다고 해서 브라우저는 나머지 HTML을 처리하고, 그 동안 다른 작업을 찾는다.

### 파서 차단 리소스

파서 차단 리소스는 브라우저가 HTML을 계속 파싱하여 다른 작업을 찾지 못하도록 하는 리소스이다. JavaScript는 실행 시 DOM 또는 CSSOM을 변경하는게 가능하므로, 기본적으로 파서 차단이다.

파서는 오나전히 처리될 때까지 파싱을 차단하는 리소스를 지나갈 수 없다. 그래서 그 이후의 콘텐츠에 엑세스하고 렌더링할 수 없다. 브라우저는 대기하는 동안 수신된 HTML을 렌더링할 수 있지만, 중요한 렌더링 경로가 우려되는 경우 `<head>`의 파서 차단 리소스는 모든 페이지 콘텐츠가 렌러딩되지 못하도록 차단한다는 의미이다.

요약 : JavaScript가 HTML 파서를 차단하는 이유

`<script>`요소에 defer, async, module 속성이 없는 경우 즉 동기인 경우 동기식 JS는 DOM을 변경할 수 있으므로 파서가 도달할 때 실행되어야 한다.

### 중요한 렌더링 경로 최적화

중요한 렌더링 경로를 최적화하려면 HTML을 수신하는데 걸리는 시간을 줄이고(첫 바이트까지의 시간 _ TTFB: Time To First Byte), 렌더링 차단 리소스의 영향을 줄여야 한다.

1. 소스 사이즈 줄이기
2. 외부에서 가져오는 리소스 줄이기 (media 쿼리 사용하기, 불필요한 파일은 나중에)
3. 외부에서 가져오는 횟수 줄이기
4. Reflow, Repaint 줄이기
