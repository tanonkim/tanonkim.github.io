## 1. 왜 이벤트로 나눴나

같은 트랜잭션에 넣으면 이렇게 된다.

| 같은 트랜잭션에서 저장                           | 생기는 일                                                             |
|--------------------------------------------------|-----------------------------------------------------------------------|
| 구매 활동 저장이 실패하면                        | 주문 확정까지 되돌아간다. PG는 이미 승인했는데 주문은 확정되지 않는다 |
| 트랜잭션 이후 기능이 늘면 (랭킹 · 포인트 · 알림) | 코드가 그 기능들을 모두 알게 되고, 하나만 느려도 커밋이 느려진다 |
| 그 기능이 다른 앱이라면                          | 트랜잭션 안에서 다른 앱을 부를 수 없다                           |

결국 하고 싶었던 것은 **주문 확정이 뒤에 오는 일을 모르게 하는 것**, 즉 결합도를 낮추는 것이었다.

Spring 이벤트(`ApplicationEvent`)로도 코드의 결합은 끊을 수 있다. 4주차 목록 캐시 무효화가 그렇게 되어 있다. 하지만 Spring 이벤트는 같은 프로세스 안에서만 전달된다. 
앱이 죽으면 처리 중이던 이벤트도 함께 사라지고, 다른 앱(commerce-streamer)은 그 이벤트를 받을 방법이 없다. 프로세스의 경계를 넘으려면 사실을 프로세스 밖에 남겨야 한다. 그래서 broker에 남기는 Kafka를 골랐다.


## 2. 언제, 어디서 보낼까

확정 트랜잭션 안에서 바로 `kafkaTemplate.send`를 부르면 두 가지가 틀어진다.

- 트랜잭션이 rollback돼도 broker에는 record가 남는다. 확정되지 않은 주문의 "확정 이벤트", 즉 발행되지 않아야 하는 이벤트다.
- broker가 느리면 결제 · 주문 · 재고 락을 가지고 기다린다.

그래서 commit 뒤에 보내기로 했다. 그다음 고민은 "commit 뒤의 어디에서"였다.

| | AFTER_COMMIT listener (선택)                                                                  | commit 뒤 오케스트레이션 |
|---|-----------------------------------------------------------------------------------------------|---|
| 방법 | 확정 트랜잭션 안에서 Spring 이벤트를 내고, `@TransactionalEventListener(AFTER_COMMIT)`가 send | 트랜잭션을 실행한 쪽이 "이번에 확정됨"을 돌려받아 그 바깥에서 send |
| 결과를 반영하는 진입점 (PG callback · 조회 · 만료 등) | 모두 같은 주문 확정 메서드를 지나므로 한 곳만 바꾼다                                          | 진입점마다 반환값을 바꾸고 send를 붙인다 |
| 위험 | 발행이 코드 흐름에서 잘 안 보인다.                                                            | 새 진입점을 만들 때 send를 빠뜨리기 쉽다 |

기준은 "덜 뜯어고치는 쪽 + 유지보수"이었다. 결제 결과가 들어오는 길은 PG callback, 주기적인 조회, 생성 응답, 만료까지 여러 개인데 모두 같은 확정 메서드를 지난다. listener 방식은 그 한 곳에서 이벤트만 내면 되고, outbox를 적용할 떄 발행 방식을 바꿀 때도 같은 자리만 고치면 된다. 오케스트레이션은 길마다 반환값을 바꾸고 send를 붙여야 해서, 길이 하나 늘 때마다 send를 빠뜨릴 자리도 하나 는다.

"실행되지 않는" 위험은 발행 기록 저장을 `Propagation.MANDATORY`로 두어 막았다. 트랜잭션 밖에서 부르면 조용히 넘어가지 않고 예외가 난다.

AFTER_COMMIT에서 `send()`는 record를 producer 버퍼에 넣고 바로 돌아온다. 실제 전송과 결과 확인은 **다른 스레드**가 한다. 그래서 PG callback 응답은 broker를 기다리지 않는다.

| 구간 (주문 10건, 1초 간격) | 첫 건 | 나머지 9건 |
|---|---:|---:|
| 확정 → broker 저장 | 617ms | 12 ~ 79ms |
| broker → 구매 활동 저장 | 87ms | 4 ~ 28ms |
| **확정 → 구매 활동** | 704ms | **17 ~ 107ms (대부분 17 ~ 31ms)** |

첫 건만 느린 것은 producer가 첫 send 때 broker에 topic 정보(metadata)를 처음 묻기 때문이다.

## 3. 보냈다는 건 어디까지 성공인가

"send가 성공했다"는 말에는 단계가 있다. 이번 주에 정한 기준은 이렇다.

- `acks=all`: leader만 받은 게 아니라 **동기화된 복제본(ISR) 전부**가 받았을 때 성공 응답을 받는다.
- topic은 복제본 3개(RF 3), `min.insync.replicas=2`: 복제본이 2개 미만이면 쓰기를 거절한다.
- 성공 응답(send 콜백)을 받으면 발행 기록 테이블에 partition · offset · 시각을 남긴다. 받지 못하면 그 행이 "미발행"으로 남는다.

broker를 꺼 보며 확인했다.

| 상태 | 결과                                                          |
|---|---------------------------------------------------------------|
| 3대 정상 | 쓰기 성공                                                     |
| 1대 정지 | 새 leader로 넘어가 쓰기 성공. 정지 전에 쓴 record도 남아 있다 |
| 2대 정지 | `NotEnoughReplicasException`으로 거절. **잃는 대신 멈춘다**   |

그런데 이 기준으로도 막지 못하는 시나리오가 있었다. 
**commit은 끝났는데 send를 부르기 전에 서버가 죽는 경우**다. 테스트에서 send 직전에 멈추게 하자, 주문은 CONFIRMED · 재고는 CONSUMED인데 broker에는 record가 없었다. send 콜백조차 오지 않았으니 실패 원인도 남지 않았고, 발행 기록의 published_at만 비어 있었다.

DB와 broker는 한 트랜잭션으로 묶이지 않는다. => outbox로 해결할 수 있다!

## 4. consume 쪽은 무엇을 책임지나

Kafka는 기본적으로 "적어도 한 번" 전달한다. 같은 record가 다시 올 수 있다는 뜻이다. 그래서 consumer는 세 가지를 지킨다.

1. **처리하고 DB에 저장한 뒤에만** offset을 commit한다. 먼저 commit하고 처리하다 죽으면 그 주문은 사라진다.
2. **같은 이벤트가 다시 와도 한 번만** 저장한다. 완료 기록에 eventId와 주문 ID를 유일 제약으로 두고, 이미 있으면 내용이 같은지 비교한다. 같으면 아무것도 하지 않고(no-op), 다르면 충돌로 보고 아래 3번처럼 DLT로 보낸다.
3. **실패하면 같은 자리에서 3번 다시 시도**하고, 그래도 안 되면 원문을 DLT에 남긴 뒤 다음으로 넘어간다. 


확인한 것:

| 장면 | 결과 |
|---|---|
| DB 저장 뒤 offset commit 전에 consumer가 죽음 | 새 consumer가 같은 위치의 record를 다시 받음 → no-op. committed offset 0 → 0 → 1, 구매 활동 2행 그대로 |
| DB 장애가 계속됨 | 1 + 3번 시도 → DLT에 원문 → 원래 offset은 다음으로 commit, 구매 활동 0행 → 원인을 없애고 DLT record를 다시 넣자 1번 저장, 한 번 더 넣어도 no-op |

## 5. consumer가 문제생기면 (사라지거나 느려지면)

여기서부터가 이번 주에 가장 오래 본 부분이다.     

### 정상 종료와 kill -9

같은 streamer 앱을 프로세스 두 개(S1 · S2)로 띄웠다. 같은 group에 consumer가 6개, partition은 3개라 셋만 일하고 셋은 대기한다. 1초에 1건씩 주문을 넣다가 10초에 S1을 껐다.


| | 정상 종료 | kill -9 |
|---|---|---|
| group에 알리나 | 예 (떠난다고 알림) | 아니오 (heartbeat가 끊길 뿐) |
| partition이 다른 consumer로 넘어가기까지 | **1.7초** | **43.3초** |
| 그동안 쌓인 주문 · 최대 대기 | 1건 · 1.7초 | 12건 · 42.7초 |
| 잃어버린 주문 · 두 번 처리 | 0 · 0 | 0 · 0 |

kill -9로 죽은 consumer는 group에 알릴 틈이 없다. group을 관리하는 broker(coordinator)는 마지막 heartbeat에서 `session.timeout.ms`(기본 45초)가 지날 때까지 그 consumer가 살아 있다고 본다. 그 사이 partition은 담당자는 있는데 아무도 읽지 않는 상태가 된다.

그래도 주문은 사라지지 않았다. record는 consumer가 아니라 broker의 partition에 쌓여 있었고, 새 consumer가 committed offset부터 순서대로 읽었다.

### 처리가 너무 느릴 때

`max.poll.interval.ms`는 poll과 다음 poll 사이에 허용되는 시간이다(기본 5분). heartbeat가 "살아 있나"를 본다면, 이 값은 "일하고 있나"를 본다. 실험에서는 10초로 줄이고, 먼저 받은 consumer가 15초 동안 poll하지 않게 했다.


| 시각 | 느린 쪽                                                 | 대기하던 쪽                                   |
|---:|---------------------------------------------------------|-----------------------------------------------|
| 4.7s | 주문 받음 → 처리 시작 (15초)                            |                                               |
| 15.1s | 10초 넘게 poll이 없어 group에서 빠짐                    | 그 partition을 받아 **같은 주문**을 다시 받음 |
| 15.3s |                                                         | 저장 → commit 성공                            |
| 19.7s | 처리 끝 → no-op → commit 거절 (`CommitFailedException`) |                                               |


## 6. 그래서 무엇을 얻었나

- **주문 확정이 빨라지고 가벼워진 느낌이다.** 확정 트랜잭션은 구매 활동을 모른다. 응답도 broker를 기다리지 않는다.
- **확장이 쉬워졌다.** 주문 뒤에 포인트를 적립하거나 푸시 알림을 보내는 일이 생겨도, 새 consumer group을 만들어 같은 topic을 읽게 하면 끝이다. 확정 코드는 손대지 않는다. group마다 committed offset을 따로 가지니, 알림이 밀려도 구매 활동은 영향을 받지 않는다.
- **앱 사이의 경계가 단순해졌다.** 서비스가 나뉜 환경이라면 producer는 발행만, consumer는 소비만 하면 된다. 서로의 API 주소도, 상대가 지금 살아 있는지도 몰라도 된다. 둘이 약속하는 것은 topic 이름과 이벤트의 모양뿐이다.
- consumer가 죽어도, broker 한 대가 죽어도 record는 남았다.
- **비용에 대한 생각이 바뀌었다.** 이번 주에 broker 3대를 띄우고 설정을 맞추는 데만 꽤 시간이 들었다. 작은 서비스 하나라면 과하다. 하지만 서비스와 팀이 많은 조직이라면, 서비스마다 서로를 직접 부르고 실패를 각자 처리하는 비용이 Kafka를 한 번 제대로 운영하는 비용보다 커질 것 같다. Kafka가 비싸다는 것보다, 연결이 늘어날수록 더 싸지는 구조라는 쪽으로 생각이 바뀌었다.

## 7. 대신 무엇이 생겼나

- **DB와 broker가 따로 논다.** commit 뒤 send 전에 죽으면 이벤트가 없다
- 같은 record가 다시 오는 것을 전제로 멱등하게 저장하는 것을 깊이 고려했고, 직접 만들어야 했다
- **장애가 오류가 아니라 느림으로 온다.** kill -9는 43초의 공백으로, 느린 consumer는 같은 일의 반복으로 나타났다. 예외 로그만 보고 있으면 모른다. => 그래서 모니터링으로 시각화해서 미리 인지하는게 중요할 것 같다.
- **설정이 많고 기본값이 함정일 수 있다.** Spring Kafka의 기본 DLT 이름은 `원래topic-dlt`인데 topic은 `.DLT`로 만들어 두어, DLT 발행이 86번 실패하는 동안 그 partition이 멈췄다. 실패한 record의 offset을 바로 commit하려면 `commitRecovered`도 따로 켜야 했다.

## 8. 확인한 것과 확인하지 못한 것

| 확인한 것 | 확인하지 못한 것 |
|---|---|
| broker 1대 정지는 쓰기 계속, 2대 정지는 거절 (정상 종료로만) | broker를 강제 종료했을 때의 ISR 변화 |
| commit 뒤 send 전에 멈추면 이벤트가 없다 (테스트의 통제된 중단) | 실제 프로세스 강제 종료로 같은 장면 |
| consumer 정상 종료 1.7초 · kill -9 43.3초 공백, 유실 0 | 여러 번 반복했을 때의 분포 |
| 느린 consumer는 쫓겨나고 같은 record가 다시 처리된다 (KafkaConsumer로) | Spring listener 컨테이너가 거절된 commit을 어떻게 다루는지 |
| 전체 흐름(주문 → broker → 구매 활동)을 두 앱으로 한 번 실행 | 부하를 걸었을 때 `max.block.ms`가 요청 스레드를 얼마나 붙잡는지 |
