## 🎯 1단계: 진입 전 준비 (2~3분)

**👁️ 이 챕터에서 다룰 내용을 예측하면?**

1부가 "장애를 견디는 안정성 패턴"이었다면, 2부는 운영 환경을 1순위로 두고 설계하는 방법을 다룰 것으로 예상. 네트워킹·모니터링·배포·보안 등 개발 환경과 다른 운영 현실이 핵심일 것.

**🧠 내가 이미 알고 있는 것은?**

1부에서 타임아웃·서킷브레이커·격벽 등 안정성 패턴과, 장애 시 가시성(모니터링)의 중요성을 사례로 학습함. 운영 환경이 개발 환경과 다르다는 점은 알지만 계층별로 체계화해 본 적은 없음.

## 📖 2단계: 독서 중 포착 (능동적 독서)

### 6장 - 경험 이야기 (운영 가시성이 만든 차이)

**💡 핵심 개념 / 코어 키워드**

- 추수감사절(성수기) 주말 장애 사례. 장애 발생 20분 후 파악한 징후:
  - 세션 수 매우 높음
  - 네트워크 대역폭 사용량 높지만 **한계치에는 도달하지 않음**
  - 애플리케이션 서버 페이지 지연시간 매우 김
  - 웹·앱·DB CPU 사용량은 **너무 낮음**
  - 검색 서버는 정상 응답, 시스템 통계 안정적
  - 요청 스레드는 거의 다 바쁨 — 대부분 **3분 이상 처리 중**
- **진단 포인트:** CPU는 낮은데 스레드는 전부 바쁨 → 연산 병목이 아니라 **스레드가 무언가를 기다리며 블로킹된 상태** (1부의 *블록된 스레드/응답 지연* 안티패턴과 동일)
- 원인: 추수감사절 주말 서버 정비 중 일부 서버가 멈춰 있었고, 남은 서버 CPU가 100%
- 해결책: **자원 풀을 0으로 설정**해 해당 경로 요청을 사실상 차단 → 남은 서버 보호 (1부의 *부하 제한* 맥락)

**🔖 핵심 결론**

- 압박 속에서도 진단하고 **금전 손실을 피할 수 있었던 건 운영 시스템의 가시성(생명징후 `모니터링`)이 좋았기 때문** → 7장 "운영 고려 설계"의 출발점

---

### 7장 - 운영 고려 설계 (7.1까지)

**💡 핵심 개념 / 코어 키워드**

- **운영 고려 설계 = 운영 문제를 최우선 설계 고려사항으로 둔다**
- 운영 환경은 개발 환경과 매우 다름: 네트워크·모니터링·로그·운영 제어·보안 포함
- **5계층 모델** (아래에서 위로 쌓임):

| 계층 | 다루는 것 |
| --- | --- |
| 운영 | 보안, 가용성, 처리 능력, 상태, 의사소통 |
| 제어평면 | 시스템 모니터링, 배치, 이상 탐지, 기능 |
| 연결 | 경로 설정, 부하 분산, 장애 극복, 트래픽 관리 |
| 인스턴스 | 서비스·프로세스·컴포넌트, 인스턴스 모니터링 |
| 기반 | 하드웨어, 가상머신, IP 주소, 물리 네트워크 |

- **7.1 데이터 센터와 클라우드의 네트워크:** 네트워크 구축은 *소켓을 열고 닫는 것 이상*의 작업을 요구함 — '기반' 계층 설명의 시작
- 이 계층 구조가 곧 2부 나머지 장의 목차 역할 (기반 → 인스턴스 → 연결 → 제어평면 → 운영)

**🔖 좋은 문장 / 인사이트**

> 운영 문제를 설계의 부차적 요소가 아니라 최우선 고려사항으로 두라.

> 네트워크 구축은 소켓을 열고 닫는 것 이상의 작업이다.

## 🔄 3단계: 내 언어로 설명하기 (Feynman 기법)

**👶 신입 개발자에게 이 챕터를 설명한다면?**

잘 만든 시스템도 운영 중엔 예상 못 한 일이 터진다. 추수감사절 사례에서 CPU는 멀쩡한데 응답이 느렸던 건 서버가 '일하느라'가 아니라 '기다리느라' 멈춰 있었기 때문이다. 이걸 빠르게 알아챌 수 있었던 건 모니터링이 잘 돼 있었기 때문 — 즉 운영 가시성이 돈을 지켜줬다. 그래서 2부는 "운영을 처음부터 설계에 넣자"고 말하며, 시스템을 기반 → 인스턴스 → 연결 → 제어평면 → 운영의 5계층으로 나눠 각 층에서 운영을 어떻게 챙길지 설명한다.

---

## 🔗 4단계: 연결 & 적용

**🛠️ 현재 프로젝트/실무에 적용할 수 있는 포인트**

- 핵심 경로에 'CPU vs 스레드 상태'를 함께 보는 대시보드 구성 (CPU 낮음 + 스레드 바쁨 = 블로킹 신호)
- 서버 정비/배포 시 남은 서버의 처리 능력 한계를 사전 산정하고, 부하 제한(자원 풀 축소·요청 차단) 시나리오 준비
- 시스템을 5계층 관점으로 점검 — 기반·인스턴스·연결·제어평면·운영 각각의 모니터링 포인트 확보

**🧱 기존에 배운 개념과 연결되는 점**

- 1부 *블록된 스레드/응답 지연* 안티패턴 → 6장 사례의 핵심 징후와 일치
- 1부 *부하 제한(Load Shedding)* → 6장 해결책(자원 풀 0 설정)
- 1부에서 강조한 모니터링·서킷브레이커 상태 가시성 → 2부 '운영 고려 설계'의 토대

**🔍 기존 코드/시스템에서 개선할 수 있는 부분**

- 스레드 풀·자원 풀 상태를 외부에서 관측/제어할 수 있는 엔드포인트 확보
- 부하 급증 시 특정 경로 요청을 차단(자원 풀 축소)할 수 있는 운영 스위치 마련

## 🎯 5단계: 복습 질문 (Active Recall)

**🤔 이 챕터에서 스스로에게 던질 질문 3가지**

1. CPU 사용률은 낮은데 모든 요청 스레드가 바쁘다면 무엇을 의심해야 하는가?
2. 6장 팀이 추수감사절 장애에서 금전 손실을 피할 수 있었던 결정적 요인은?
3. 운영 고려 설계의 5계층(기반·인스턴스·연결·제어평면·운영)과 각 층의 관심사를 설명할 수 있는가?
