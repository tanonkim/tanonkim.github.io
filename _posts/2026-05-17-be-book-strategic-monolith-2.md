## 🎯 1단계: 진입 전 준비

**👁️ 이 챕터에서 다룰 내용을 예측하면?**

서브시스템 간 통신을 어떻게 하는지, 동기/비동기 방식의 차이와 장단점을 다룰 것 같다. Kafka나 RabbitMQ 같은 메시지 큐가 왜 필요한지도 나올 듯.

**🧠 내가 이미 알고 있는 것은?**

- W사에서 ActiveMQ를 직접 구현해봄 → 실제로 메시지를 던지고 받는 구조는 안다
- 동기 REST 호출은 호출한 쪽이 응답을 기다려야 해서 장애가 전파됨
- Kafka = 분산 메시지 스트리밍 플랫폼 정도는 알고 있음

## 📖 2단계: 독서 중 포착

**💡 핵심 개념**

- **분산 시스템 동기화의 어려움** — 여러 서브시스템이 얽힌 큰 유스케이스를 동기 방식으로 처리하면, 한 곳에서 실패하면 **전체가 실패한다. 장애가 전파된다.**
- **메시지/이벤트 주도 아키텍처** — 비동기 메시지와 시간적 분리(temporal decoupling)로 `장애 전파를 막으면서 복잡한 다단계 프로세스를 수행`
- **코레오그래피(Choreography)** — 중앙 지휘자 없이 각 서비스가 이벤트를 보고 스스로 반응. 단순한 다단계 유스케이스에 적합
- **오케스트레이션(Orchestration)** — 중앙 오케스트레이터가 전체 흐름을 제어. 복잡한 다단계 프로세스에서 가시성이 높음
- **메시지 버스** — 이벤트를 발행(Publish)하고 구독(Subscribe)하는 중간 채널. **발행자는 누가 소비할지 몰라도 됨** → 느슨한 결합 달성. (구현체: Kafka, RabbitMQ, ActiveMQ)
- **이벤트 소싱(Event Sourcing)** — 엔티티의 현재 상태가 아닌, 시간 순서대로 발생한 이벤트 스트림을 저장. 과거 상태를 재현할 수 있음
- **CQRS** — Command(쓰기)와 Query(읽기) 모델을 분리. 읽기/쓰기 각각 독립적으로 최적화·확장 가능
- **REST의 역할** — 이벤트 로그를 소비자에게 제공할 때 REST 사용. 이유: 모든 개발자가 HTTP를 이해하고, 정적 콘텐츠 제공이 빠름

**🔑 핵심 비교표**

| 구분 | 코레오그래피 | 오케스트레이션 |
| --- | --- | --- |
| 제어 방식 | 분산 (각 서비스가 자율) | 중앙 집중 (오케스트레이터) |
| 적합한 경우 | 단순 다단계 유스케이스 | 복잡한 다단계 프로세스 |
| 가시성 | 낮음 (흐름 파악 어려움) | 높음 (한 곳에서 전체 흐름 파악) |
| 결합도 | 매우 느슨 | 오케스트레이터에 의존 |

**❓ 처음에 이해 안 됐던 것 → 해소**

> **메시지 버스**: 서브시스템들이 직접 전화하면 선이 엉킨다. 메시지 버스는 공용 우편함. A 서비스는 이벤트를 버스에 던지고, B·C 서비스는 필요한 이벤트만 골라 구독한다. 서로를 직접 알 필요 없음.

> **CQRS — 왜 필요한가**: 읽기(조회)가 쓰기보다 압도적으로 많은 시스템에서, 둘이 같은 모델을 쓰면 서로의 최적화를 방해한다. Command(쓰기)는 정규화 DB, Query(읽기)는 비정규화 뷰로 분리하면 각각 독립적으로 최적화·확장 가능.

> **CQRS의 트레이드오프**: 읽기 모델(비정규화)은 쓰기가 발생할 때마다 동기화해줘야 해서 정합성 관리가 복잡해진다. 이걸 해결하는 방법이 이벤트 소싱 → Command 쪽에서 이벤트를 발행하면, Query 모델이 이벤트를 구독해서 자동으로 읽기 뷰를 갱신한다. 복잡성을 없애는 게 아니라 이벤트로 흐르게 구조화하는 것.

**🔖 인상 깊은 문장**

> *"비동기 메시지 및 시간적 분리로 인한 장애 전파를 방지하면서 복잡한 다단계 프로세스를 수행"*

## 🔄 3단계: 내 언어로 설명하기 (Feynman)

**👶 신입 개발자에게 코레오그래피 vs 오케스트레이션을 설명한다면?**

식당에 비유하면 이렇다. **오케스트레이션**은 매니저(오케스트레이터)가 "주방팀, 지금 3번 테이블 파스타 만들어. 완성되면 서빙팀 불러." 하고 전체 흐름을 지시한다. **코레오그래피**는 매니저 없이, 주방팀이 파스타를 완성하면 "파스타 완성" 이벤트를 외치고, 서빙팀이 그 소리를 듣고 알아서 가져가는 방식이다. 코레오그래피는 각자 자율적이라 단순할 땐 빠르지만, 10단계짜리 복잡한 주문이 생기면 흐름을 추적하기가 어렵다.

**메시지 버스와 이벤트 소싱을 묶어서 설명하면?**

쇼핑몰에서 "주문 완료" 이벤트가 발생했다고 하자. 이 이벤트를 Kafka(메시지 버스)에 던지면, 결제 서비스·알림 서비스·재고 서비스가 각자 구독해서 처리한다. 이벤트 소싱은 이 이벤트들을 버리지 않고 DB에 순서대로 쌓아둔다. 덕분에 "6개월 전 이 주문 당시 재고가 몇 개였지?" 같은 질문에도 이벤트를 재생해서 답할 수 있다.

## 🔗 4단계: 연결 & 적용

**🛠️ W사 프로젝트 실무 연결**

- W사에서 **ActiveMQ로 메시지 서버를 직접 구현**한 것이 이 챕터의 메시지 버스 패턴 그 자체다
- 현재 구현이 코레오그래피인지 오케스트레이션인지 파악해볼 것 → 중앙에서 흐름을 제어하는 로직이 있으면 오케스트레이션에 가까움
- 만약 특정 이벤트 처리 실패 시 재시도·보상 트랜잭션이 필요하다면 → 오케스트레이션 패턴 도입 고려

**🧱 기존 지식과 연결**

- **Ch.8 확장성 문제** → CQRS로 연결: 읽기가 많은 서비스에서 모놀리스 전체를 스케일 아웃하는 대신, Query 모델만 따로 확장 가능. 이전 챕터와 직결됨
- **@Async + 스레드 분리** (이전 학습) → 모놀리스 내부에서 비동기 처리를 흉내낸 것. 이벤트 주도 아키텍처는 이걸 서비스 간 레벨로 확장한 개념
- **Spring의 ApplicationEvent** → 같은 JVM 내에서 코레오그래피를 구현하는 방식. Kafka는 서비스 간 코레오그래피

**🔍 코드/설계에서 개선 고려 포인트**

- 메시지 브로커 기반 구현이라면, 이벤트가 실패했을 때 재처리(Dead Letter Queue) 전략이 있는가?
- 조회가 많은 API에서 CQRS 도입 시 읽기 전용 뷰 테이블이나 Redis 캐시를 Query 모델로 쓸 수 있음
