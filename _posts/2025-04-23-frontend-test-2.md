## 2.1 테스트 범위와 목적

### 2.1.1 테스트 범위

웹 애플리케이션은 여러 모듈을 조합해서 만든다.

- 라이브러리가 제공하는 함수
- 로직을 담당하는 함수
- UI 관련 함수
- 웹 API 클라이언트
- API 서버
- 데이터베이스 서버

프론트엔드 개발의 테스트 범위는 크게 네가지로 분류한다.

1. 정적 분석

   TS나 ESLint가 제공하는 기능을 활용한다.

2. 단위 테스트

   한 가지 모듈에 대해 해당 모듈이 제공하는 기능을 테스트한다.

3. 통합 테스트

   모듈 조합으로 제공되는 기능을 검증하는 테스트이다.

4. E2E 테스트

   헤드리스 브라우저나 UI 자동화 도구를 결합하여 검증하는 테스트이다.

### 2.1.2 테스트 목적

테스트 목적에 따라 분류되는데, 기능테스트, 비기능 테스트, 화이트박스 테스트, 회기 테스트가 있다.

1. `기능 테스트`(인터렉션 테스트)

   개발된 기능에 문제가 없는지 검증하는 테스트이다.

2. `비기능 테스트` (접근성 테스트)

   신체적, 정신적 특성에 따른 차이 없이 동등하게 제품을 사용할 수 있는지 검증하는 테스트이다.

   최근 전 세계적으로 웹 접근성 관련 API가 여러 플랫폼에 추가되어 테스트를 자동화할 때 객관적으로 검증할 수 있는 환경이 갖추어지고 있다.

3. `회기 테스트`

   특정 시점을 기준으로 전후 차이를 비교하며 문제가 있는지 검증하는 테스트이다.

## 2.2 프론트엔드 테스트의 범위

### 2.2.1 정적 분석

- TS

타입스크립트를 활용하는 정적분석은 버그를 조기에 발견할 수 있도록 한다.

```javascript
function getMessage(name : string | undefined) {
	const a = name; // string | undefined
	if (!name) {
		return 'Hello anonymous';
	}
	const b = name; // b is always string
	return `Hello ${name}!`	
}
```

- ESLint

코드 가이드라인을 제공하는 ESLint도 정적 분석 도구 중 하나이다. 부적절한 구문을 수정해서 잠재적으로 발생할 수 있는 버그를 사전에 방지한다.

```javascript
useEffect(() => {
	console.log(name);
}, []) // 참조중인 name을 누락해서 Lint 오류
```

### 2.2.2 단위 테스트

Unit Test는 기초적인 테스트이다. 테스트할 모듈이 특정 입력값을 받아 기대하는 출력값을 반환하는지 테스트한다.

### 2.2.3 통합 테스트

통합테스트는 여러 모듈을 연동한 기능을 테스트한다. 커다란 UI 컴포넌트는 여러 모듈을 조합해 기능을 제공하며, 기능은 주로 인터랙션에서 시작된다.

예)

1. select 박스를 조작한다.
2. URL 검색 쿼리가 변경된다.
3. 검색 쿼리가 변경되어 데이터 API가 호출된다.
4. 목록 화면을 갱신한다.

→ select 박스를 조작하는 인터랙션을 시작으로 최종적으로 목록 화면 내용을 갱신하는 처리가 이뤄진다. (1을 실행하면 4도 실행된다와 같은 테스트)

### 2.2.4 E2E 테스트

E2E테스트는 UI테스트 뿐만 아니라 외부 스토리지와 같이 연동 중인 하위 시스템을 포함하는 테스트이다. 입력 내용에 따라 저장된 값이 갱신되기에 UI는 물론 연동된 외부 기능이 정상적으로 작동하는지 검증이 가능하다.

## 2.3 프론트엔드 테스트의 목적

### 2.3.1 기능 테스트(인터렉션 테스트)

웹 프론트엔드의 주요 개발 대상은 사용자가 조작할 UI 컴포넌트이다. 이런 특성 때문에 웹프론트엔드의 `기능테스트`는 `인터렉션 테스트`가 대부분이다.

### 2.3.2 비기능 테스트(접근성 테스트)

접근성 테스트는 비기능 테스트의 한 종류이다.

키보드만으로 웹사이트를 이용할 수 있는지, 명암비가 시인성에 문제는 없는가와 같은 다양한 검증 항목이 있다.

예) 사례

체크박스를 체크할 수 있다.

오류 응답을 받았을 때 오류 문구를 렌더링한다.

렌더링 화면에 접근성 위반 사례가 있는지 검사한다.

### 2.3.3 시각적 회기 테스트

CSS는 UI 컴포넌트에 정의된 스타일 뿐만 아니라 브라우저에 적용된 모든 스타일의 영향을 받는다.

회기 테스트 중 하나인 시각적 회귀 테스트는 헤드리스 브라우저에 그려진 내용을 캡쳐하여 캡처된 이미지 간 차이를 검증한다. 사용자 조작으로 변경된 화면까지 갭쳐하여 비교한다.

예) 사례

버튼 스타일에 차이가 없다.

메뉴 바를 열었을 때 화면에 차이가 없다.

렌더링 된 화면에 차이가 없다.

## 2.4 테스트 전략 모델

![](/assets/img/2025-04-23/frontend-test-2-1.png)

상층부 테스트는 많은 시간과 비용이 필요하다. 최대한 실제환경과 유사한 환경을 구축해야 하고, 테스트 할 때마다 제품과 연동된 외부 시스템의 응답도 기다려야 한다.

### 2.4.1 아이스크림콘과 테스트 피라미드

아이스크림콘 모델 ↔ 테스트 피라미드

상층부 테스트 비중이 높은 아이스크림 콘은 안티패턴으로 자주 언급되는 테스트 전략모델이다. 운용 비용이 높고 외부 모듈의 의존성 때문에 실패가 있을 수 있는 불안정한 테스트가 많다.

테스트 피라미드는 하층부의 테스트 비중이 높을 수록 안정적이고 가성비 높은 테스트가 가능하다

### 2.4.2 테스팅 트로피

이 모델의 핵심은 통합 테스트 비중이 가장 높아야 한다는 것이다.

![](/assets/img/2025-04-23/frontend-test-2-2.png)

프론트엔드 개발에서 단일 UI 컴포넌트로 구현되는 기능은 거의 없다. 테스팅 트로피에서는 사용자 조작을 기점으로 한 통합 테스트의 비중이 높을수록 더욱 우수한 테스트 전략이라는 의도가 있다.

## 2.5 테스트 전략 기획

테스트 전략 모델을 참고해 프로젝트에 최적인 전략을 수립하려면 테스트 대상 및 목적에 따른 판단 기준을 정립해야 한다.

### 2.5.1 테스트가 없어 리팩터링이 불안한 경우

릴리즈된 프로젝트에 테스트 코드가 없으면 리택터링이 불안할 수 있다. 이 때는 먼저 릴리즈된 기능을 목록으로 정리해야 한다. 정리 후 변경 전후로 결함이 발생하지 않았는지 검증하는 회귀 테스트를 작성한다.

웹 API 서버에 대한 의존성이 깔끔하게 분리되지 않으면 테스트 작성이 어렵다. 이 때 Mock 서버를 활용하여 통합 테스트를 실시한다.

### 2.5.2 반응형으로 제작된 프로젝트

반응형 웹은 하나의 HTML에서 여러 형태의 화면을 제공한다. 반응형 웹은 테스팅 라이브러리만으로 스타일을 포함한 세밀한 테스트가 어렵다. 이 때 시각적 회귀 테스트가 유용하다.

### 2.5.3

Mock서버가 아닌 실제 웹 API 서버를 활용해서 E2E 테스트를 하고 싶으면 테스트용 스테이징환경을 사용해야 한다.

테스트용 컨테이너를 활용해서 CI 호나경에서 실행 후, 연동 중인 여러 시스템과 함께 테스트가 가능하다. 비교적 환경 구축 비용이 적고 개발자 혼자서도 구축할 수 있는 장점이 있다.
