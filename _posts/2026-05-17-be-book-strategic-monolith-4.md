## 📖 2단계: 독서 중 포착

**💡 핵심 개념**

- **MSA 수는 비즈니스/기술 타당성으로 결정** — 유행이라서 MSA가 아니라, 필요해서 MSA다
- **두 가지 전환 접근방식** — ① MSA에서 모놀리스 일부를 보존 ② 모놀리스를 완전히 MSA로 교체
- **분산 컴퓨팅의 잘못된 믿음 8가지** — 네트워크는 안정적, 지연=0, 대역폭=무한, 안전, 토폴로지 불변, 관리자 1명, 전송비용=0, 균질한 네트워크. **실제로는 모두 거짓**
- **필수 복원력 패턴** — 장애감시자, 서킷브레이커, 지수 재시도, 멱등 수신자, 순서 벗어난 메시지 처리, 로드셰딩/오프로딩/백프레셔
- **빅볼 오브 머드 → MSA 6단계** — 비즈니스 역량 파악 → 우선순위화 → 관련성 파악 → 추출 결정 → 첫 번째 추출 계획 → 반복
- **단일 데이터 소스 원칙** — 각 데이터는 반드시 하나의 서비스만 소유해야 한다
- **데이터 조화 3가지 패턴** — DB 트리거 / 이벤트 서피싱 / CDC(데베지움)

**🔑 핵심 비교표**

| 패턴 | 방식 | 레거시 코드 수정 | 적합한 상황 |
| --- | --- | --- | --- |
| DB 트리거 | 변경 시 트리거 → 이벤트 테이블 삽입 | 불필요 | 단순 변경 감지 |
| 이벤트 서피싱 | 코드에서 직접 이벤트 테이블 기록 | 필요 | 명시적 이벤트 설계 |
| CDC (데베지움) | DB 트랜잭션 로그 읽기 → Kafka 발행 | 불필요 | 레거시 코드 손대기 어려울 때 |

**❓ 처음에 이해 안 됐던 것 → 해소**

> **`토폴로지`**: 서비스들이 연결된 네트워크 구조. MSA에선 컨테이너 재시작마다 IP가 바뀌고 서비스가 추가/삭제되므로 구조가 계속 변한다. "토폴로지 불변" 믿음이 위험한 이유.

> **로드셰딩**: 서버 과부하 시 일부 요청을 의도적으로 거부. 지하철 만원이면 다음 열차 타라고 하는 것.

> **오프로딩**: 처리 못할 요청을 큐에 넘겨 나중에 처리. 창구에서 번호표 주고 기다리게 하는 것.

> **`백프레셔`**: 소비자가 생산자에게 "천천히 보내줘" 신호. 주방이 바쁘면 홀에서 주문을 잠시 중단하는 것. Spring WebFlux Reactive Streams에 기본 내장.

> **데이터 조화 전체 그림**: 레거시 → MSA 전환 과도기에 레거시 DB와 새 MSA DB가 동시에 존재. 두 DB의 데이터를 항상 동기화해야 하는 문제가 "데이터 조화"다.
>
> [과도기 상황]<br>
> 레거시 코드 → 레거시 DB ──┐<br>
> ├── 동기화 필요 (데이터 조화)<br>
> 새 MSA 코드  → 새 MSA DB ──┘
>
> 해결책:<br>
> DB 트리거    → 트리거가 이벤트 테이블 자동 기록 → 새 MSA가 폴링<br>
> 이벤트 서피싱 → 레거시 코드가 직접 이벤트 테이블 기록<br>
> CDC(데베지움) → DB 트랜잭션 로그 읽기 → Kafka → 새 MSA 소비
>
> **데베지움이 왜 필요한가**: 레거시 코드는 방대해서 직접 수정하기 어렵다. 데베지움은 코드 한 줄도 안 건드리고 DB 로그(binlog, WAL)만 읽어서 변경을 감지한다. 레거시에 **비침투적**으로 MSA 전환이 가능.

**🔖 인상 깊었던 문장**

> *"레거시에서 MSA로 전환하는 가장 간단한 방법은 잘 모듈화된 모놀리스로 시작하는 것"*

> *"분산 컴퓨팅은 복잡한 문제를 야기하지만, 모놀리식 아키텍처를 사용하면 대부분 피할 수 있다"*

## 🔄 3단계: 내 언어로 설명하기 (Feynman)

**👶 신입 개발자에게 서킷브레이커와 데이터 조화를 설명한다면?**

**서킷브레이커**: 전기 차단기와 같다. 결제 서비스가 응답을 못 하면 주문 서비스가 계속 기다리다가 같이 죽는다. 서킷브레이커는 "결제가 5번 연속 실패하면 더 이상 시도하지 않고 바로 실패 응답을 돌려줘. 30초 후에 다시 한 번 해봐"라고 동작한다. 장애가 연쇄적으로 퍼지는 걸 차단한다.

**데이터 조화**: 회사 이전할 때 두 사무실을 동시에 쓰는 기간이 생긴다. 구 사무실 서류와 신 사무실 서류가 항상 같아야 하는데, 누군가 구 사무실에서 계약서를 수정하면 신 사무실에도 자동으로 반영되어야 한다. 이 동기화를 DB 트리거/이벤트 서피싱/CDC 중 하나로 구현하는 것이 데이터 조화다.

## 🔗 4단계: 연결 & 적용

**🛠️ W사 프로젝트 실무 연결**

- W사가 언젠가 MSA로 전환한다면 6단계 절차대로 **비즈니스 역량 파악부터** 시작해야 한다. 한 번에 전부 바꾸려 하면 실패한다
- 현재 W사는 단일 DB를 쓰는 모놀리스인데, 특정 모듈(예: 알림, 배치)을 MSA로 분리한다면 **CDC(데베지움) + Kafka** 조합이 코드 수정 없이 데이터를 동기화하는 가장 현실적인 선택
- W사에서 ActiveMQ(Ch.9)를 이미 쓰고 있으므로 데베지움 → Kafka → 새 MSA 소비 흐름이 자연스럽게 이어짐

**🧱 기존 지식과 연결**

- **Ch.8 확장성** → 서킷브레이커, 백프레셔가 Ch.8의 "리소스 집약적 부분 독립 확장"을 안전하게 만드는 보완재
- **Ch.9 이벤트 소싱** → CDC가 이벤트 소싱 패턴의 인프라 레벨 구현. 코드 대신 DB 로그가 이벤트 스트림이 됨
- **Ch.10 바운디드 컨텍스트 DB 분리** → 11장의 데이터 조화 문제가 바로 그 분리 과정에서 생기는 문제. 10장이 "왜 분리하나", 11장이 "분리할 때 데이터를 어떻게 동기화하나"
- **HikariCP 커넥션 풀** → MSA 전환 시 서비스마다 커넥션 풀을 따로 가지므로 풀 사이즈 계산이 더 중요해짐

**🔍 코드에서 점검해볼 포인트 (체크리스트)**

- 배치 서비스나 알림 기능이 MSA로 분리될 때 공유하는 테이블이 있는가? → 데이터 조화 전략 필요
- 외부 API 호출 시 실패했을 때 지수 백오프 재시도가 적용되어 있는가?
- REST 호출이 실패했을 때 서킷브레이커(Resilience4j)가 적용되어 있는가?

## 🎯 5단계: 복습 질문 (Active Recall)

> ⚠️ 지금 답 적지 말 것. 3일~1주일 후에 책 없이 답해보는 것이 진짜 복습이다.

1. **MSA 전환 시 "단일 데이터 소스" 원칙이란 무엇인가? 두 서비스가 같은 테이블을 공유하면 구체적으로 어떤 문제가 생기는가?**

   **답**

   - 각 서비스는 자신의 데이터만 소유, 다른 서비스의 데이터에 직접 접근하지 않는다.

     DB를 서비스 밖으료 노출하지 않고, API를 통해 요청

     예) 주문서비스/배송서비스 → 주문DB/배송DB

   - 같은 테이블 사용 시
     - 스키마 변경 시 양쪽 서비스 동시 배포
     - 한 서비스 쿼리가 타 서비스 영향
     - 비즈니스 로직이 DB에 분산
     - 독립 배포/스케일아웃 불가
     - 트랜잭션 범위가 확장됨 → 데드락

2. **데베지움(CDC)은 DB 트리거, 이벤트 서피싱과 비교해서 어떤 상황에서 선택해야 하는가? 레거시 코드를 수정할 수 없을 때 왜 CDC가 유리한가?**

   **답**

   데베지움 : 데이터베이스에 Insert or Update or Delete가 발생할 경우 이를 감지하고 변경 내용을 캡처해 이벤트로 변환하는 도구 → 오픈소스 분산 플랫폼

   |  | DB 트리거(SQL 로직) | 이벤트 서피싱(publish) | 데베지움(CDC) |
   | --- | --- | --- | --- |
   | 코드수정 필요여부 | 필요 | 필요 | X |
   | 레거시 호환 | 어려움 | 어려움 | Good |
   | 이벤트 누락 위험 | X | 높음(직접 수정시) | X |
   | 성능영향 | 영향도 높음(동기실행) | 낮음 | 낮음(비동기) |
   | 적합한 상황 | 감사로그, 소규모 트래픽 | 신규개발, 코드 수정 가능, 이벤트 정의가 명확할 때 | 레거시 코드가 수정 불가할 때, MSA 전환, 멀티소비자 이벤트 필요 시 |

   데베지움은 어떤 경로로 데이터를 수정하든 100%감지된다 (JDBC, 배치, RAW SQL 등)

   이벤트 서피싱은 코드에서 명시적으로 이벤트 발행 → 외부 배치 툴/DBA 등이 수정한 데이터는 누락됨

3. **서킷브레이커가 없을 때 MSA에서 장애가 어떻게 연쇄 전파되는가? W사처럼 모놀리스 내 @Async 비동기 처리와 MSA 간 서킷브레이커의 차이는?**

   **답**

   - 서빗브레이커 없는 상황

     클라이언트 ↔ API GateWay ↔ 주문서비스 ↔ 결제 서비스 (응답지연 시)

     - 타임아웃 전파, 커넥션 풀 고갈, 스레드 점유 ⇒ 시스템 전체 다운

   - 서킷 브레이커 있는 상황

     클라이언트 ↔ API GateWay ↔ 주문서비스 ↔ 서킷브레이커 ↔ 결제 서비스 (응답지연 시)

     Fallback 응답 → 일시불가 안내/나머지 서비스 정상

   **@Async 비동기 처리와 MSA 간 서킷브레이커의 차이**

   |  | 모놀리스 `@Async` | MSA 서킷브레이커 |
   | --- | --- | --- |
   | **목적** | 같은 프로세스 내에서 비동기 처리 (알림, 이메일 등) | 원격 서비스 호출 실패를 차단하고 격리 |
   | **장애 격리** | 메인 스레드는 분리되지만, 앱 전체는 같은 프로세스 | 호출 자체를 차단 → 타 서비스 완전 격리 |
   | **네트워크 장애** | 해당 없음 (JVM 내부 호출) | 네트워크 타임아웃·연결 실패 직접 처리 |
   | **상태 관리** | 없음 | CLOSED → OPEN → HALF-OPEN 상태 전이 |
   | **폴백** | 예외 처리로 직접 구현 | `fallback` 메서드 자동 호출 |

   `@Async`는 흐름과 흐름을 분리하는 개념

   MSA : 의존성 장애를 물리적으로 차단

**💬 한 줄 요약**

MSA 전환의 핵심은 기술이 아니라 비즈니스 역량 기반의 점진적 분리이며, 데이터 동기화가 가장 어려운 문제다.
