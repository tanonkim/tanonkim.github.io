### 핵심 주제: 의존성을 이용해 설계 진화시키기

설계의 핵심은 **의존성**입니다. 좋은 설계는 의존성을 어떻게 관리하느냐에 달려있고, 의존성에 따라 설계가 바뀐다.

### 1. 의존성(Dependency)이란?

설계란 코드를 어떻게 배치할 것인가에 대한 의사결정

어떤 클래스, 패키지, 프로젝트에 어떤 코드를 넣을지 결정하는 것으로 핵심은 변경에 초점을 맞추는 것이다. → 같이 변경되는 코드는 같이 모아두어야 한다.

**클래스 의존성의 4가지 종류**

1. **연관관계**: 영구적인 관계 (객체 참조로 구현)
2. **의존관계**: 일시적인 관계 (파라미터, 리턴타입, 지역변수)
3. **상속관계**: 구현이 변경되면 영향받음
4. **실체화 관계**: 시그니처가 바뀌면 영향받음

### 2. 설계 가이드 4가지

1. 양방향 의존성을 피하라 - A↔B 양방향이면 하나의 클래스를 억지로 분리한 것과 같음
2. 다중성이 적은 방향을 선택하라 - 컬렉션을 인스턴스 변수로 갖지 않도록
3. 의존성이 필요없다면 제거하라
4. 패키지 사이의 의존성 사이클을 제거하라 - 3개 패키지가 사이클이면 하나의 패키지로 봐야 함

### 3. 예제: 배달앱 주문 시스템

배달앱에서 사용자가 메뉴를 선택해 장바구니에 담고 주문하는 플로우

장바구니 정보가 로컬에 저장되어 있으므로, 주문 시점에 가게 메뉴와 일치하는지 검증이 필요.

**주문 Validation 항목**

- 가게가 영업 중인지
- 최소 주문 금액 이상인지
- 메뉴 이름과 주문 항목이 일치하는지
- 옵션 그룹/옵션의 이름과 가격이 같은지

### 4. 객체 참조의 문제점

1. **성능 문제**

- ORM 사용 시 Lazy 로딩 문제 발생
- 객체 그룹의 조회 경계가 모호해짐
- 모든 객체가 연결되어 있는 것이 근본적 문제

1. 트랜잭션 경계 문제

- 변경 빈도가 다른 객체들이 하나의 Long 트랜잭션으로 묶이면 성능 저하
- 예: 주문(Order), 가게(Shop), 배달(Delivery)은 변경 주기가 다름

### 5. 해결 방법: 객체 참조 끊기

원칙

- 함께 생성되고 삭제되는 객체끼리 묶는다
- 도메인 제약사항을 공유하는 객체끼리 묶는다
- 가능하면 분리한다

구현방식

- 경계 안: 객체 참조로 접근 (FetchType, Cascade 적용)
- 경계 밖: ID를 이용해 접근 (Repository 통해 조회)

### 6. 패키지 의존성 사이클 제거 3가지 방법

1. 새로운 객체로 변환

   중간에 추상적인 객체 만들기(DIP)

   OptionGroup, Option과 같은 추상화된 객체 도입

2. 의존성 역전(DIP)

   인터페이스를 이용해서 의존성 방향을 역전

3. 새로운 패키지 추가

   의존성 사이클을 제거하면 새로운 도메인이 발견됨

   예) 주문에서 정산 패키지 분리

### 7. 도메인 이벤트 활용

순차적으로 진행되는 도메인 로직(A 상태 변경 → B 상태 변경)을 느슨하게 결합하는 방법

```java
Order.delivered() → OrderDeliveredEvent 발행 → 이벤트 핸들러에서 처리
```

### 8. 응집도에 대한 관점

절차지향과 객체지향, 그리고 응집도

때로는 절차지향이 객체지향보다 좋을 때가 있다. 예) OrderVaildator처럼 validation 로직을 한 곳에 모아두면 비즈니스 플로우가 한 눈에 보인다.

변경주기가 다른 코드(Validation과 주문 처리)가 한 곳에 있으면 응집도가 낮아진다.

언제 절차지향에서 객체지향으로 바꿀까? Validation이 점점 커질때, 순수함수가 아닐 때
