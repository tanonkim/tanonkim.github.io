## Part2 분산 데이터

저장소와 데이터 검색에 여러 장비가 관여한다면 무슨 일이 일어날까

`확장성` - 데이터 볼륨, 읽기 부하, 쓰기 부하가 단일 장비에서 다룰 수 있는 양보다 커지면 부하를 여러 장비로 분배할 수 있다.<br>`내결함성/고가용성` - 장비 하나가 죽더라도 애플리케이션이 계속 동작해야 한다면 여러 장비를 사용해 중복성을 제공할 수 있다. <br>`지연시간` - 전 세계에 사용자가 있다면 사용자와 지리적으로 가까운 곳의 데이터센터에서 서비스를 제공하기 위해 전 세계 다양한 곳에서 서버를 두고 싶을 것. → 네트워크 패킷이 지구 반 바퀴를 돌아서 올 때까지 기다릴 필요가 없다.

### 고부하로 확장

고부하로 확장이 필요하다면 더 강력한 장비를 구매하는 것이 간단한 방법(성능 _ 수직 확장)

공유 메모리 아키텍쳐에서는 모든 구성 요소를 단일 장비처럼 다룰 수 있다.

공유 메모리 아키텍쳐 : 제한적인 내결함성을 다룬다. <br>공유 디스크 아키텍쳐 : 독립적인 CPU와 RAM을 탑재한 여러 장비를 사용, 데이터 저장은 공유하는 디스크 배열에

#### 비공유 아키텍쳐 - 수평 확장

RAM, CPU 디스크를 독립적으로 사용. 특별한 하드웨어를 필요로 하지 않기에 가격대비 성능이 가장 좋은 시스템으로 사용 가능

#### 복제 대 파티셔닝

복제 - 복사본을 다른 위치의 여러 노드에

파티셔닝/샤딩 - 데이터를 여러 파티션으로 나누는 것 //데이터를 여러 DB/서버로 분산하는 것

### 5장 복제

네트워크로 연결된 여러 장비에 동일한 데이터의 복사본을 유지

- 지리적으로 사용자와 가깝게 - 지연시간 줄임
- 시스템의 일부에 장애가 발생해도 지속적으로 동작
- 읽기 트랜잭션 → 읽기 처리량 확장

**복제방식**

단일 리더, 다중 리더, 리더리스

#### 리더와 팔로워(master / slave)

Master, Primary, leader

Slave, Secondary, follower

#### 동기식 대 비동기식 복제

**동기식**

- 리더와 일관성있게 최신 데이터 복사본을 가지는 것을 보장한다.

  갑자기 리더가 작동하지 않아도 데이터는 팔로워에서 계속 사용할 수 있음

- 동기 팔로워가 응답하지 않는다면 쓰기가 처리될 수 없다.

  → 모든 팔로워가 동기식인 상황은 비현실적이다.

**반동기식**

동기식 팔로워가 사용될 수 없게 되거나 느려지면 비동기식 팔로워 중 하나가 동기식이 된다.

- 리더와 하나의 동기 팔로워에 데이터의 최신 복사본이 있는 것을 보장한다.

**비동기식**

보통 리더 기반 복제는 완전히 비동기식으로 구성한다.

- 리더에 문제 발생 + 복제되지 않은 데이터가 있다면 유실됨. : 쓰기 작업이 지속성을 보장할 수 없다.
- 모든 팔로워가 잘못 되더라도 리더가 쓰기 처리를 계속 할 수 있다.

**팔로워장애**

- 마지막 트랜잭션 알아내기 → 그 이후의 요청을 다 따라잡기

**리더 장애 - failover**

- 수동 복구/자동 복구

1. 리더가 장애인지 파악. (타임아웃 등)
2. 새로운 리더 선출
3. 새로운 리더 사용을 위해 시스템 재설정 (시스템은 이전 리더가 팔로워가 되고, 새로운 리더를 인식할 수 있게끔 해야 한다.)

#### 복제 로그 구현

- 구문 기반 복제

  리더는 모든 쓰기 요청을 기록하고 쓰기를 실행한 다음 구문 로그(CRUD)를 팔로워에게 전송

  복제가 깨질 수 있는 다양한 사례가 존재함

  ⇒ 다른 복제 방법을 사용

- 쓰기 전 로그 배송

  모든 쓰기는 로그에 기록 →

  로그 구조화 저장소 엔진의 경우 로그 자체가 저장소의 주요 부분 ????

  B트리의 경우 모든 변경은 쓰기 전 로그에 기록 → 복원 가능

- 논리적 로그 복제
- 트리거 기반 복제

#### 복제 지연 문제(Lag)

복제는 내결함성에만 필요한 것만 아님. 확장성 + 지연시간

대부분 읽기 요청이 많아서 팔로워 간 읽기 요청을 분산. → 리더 부하를 없애고, 근처 복제 서버에서 읽기 요청을 처리

**최종적 일관성**

비동기 팔로워에서 데이터를 읽을 때 팔로워가 뒤쳐진다면 지난 정보를 볼 수 있음 → 다른 결과 : 일시적인 상태

**자신이 쓴 내용 읽기 - 쓰기 후 읽기 일관성**

사용자가 쓰기를 수행한 직후 데이터 읽기 → 바로 팔로워에게 데이터 전송하지 않고 읽기 (데이터를 자주 읽지만 가끔 쓰는 경우에 유용)

**단조읽기**

비동기식 팔로워에서 발생 - 시간이 거꾸로 흐르는 현상 ⇒ 이런 현상이 발생하지 않음을 보장한다.

파티셔닝/샤딩된 데이터베이스에서 발생하는 특징적인 문제 (읽기는 문제가 될 수 있음, 쓰기의 전역 순서는 없음)

**해결책**

트랜잭션(데이터베이스 차원)

#### 다중 리더 복제

리더가 하나만 존재하고, 해당 리더를 거쳐야만 한다면 이 때 만약 리더에 연결 불가하다면 DB에 쓰기 X

**다중 데이터센터 운영**

일반적인 리더 기반 복제 설정은 리더가 하나의 데이터 센터, 모든 쓰기는 해당 데이터 센터 거쳐야 함.

다중 리더 설정은 각 데이터센터마다 리더가 존재할 수 있음

장점

단일 → 리더가 있는 데이터센터로 이동 : 쓰기에 지연이 늘리는 원인

다중 리더 → 로컬 데이터센처에서 처리 후 비동기방식으로 다른 데이터센터에 복제 : 성능이 더 좋아짐(네트워크 지연)

오프라인 작업 할 때

단점 : 동일한 데이터를 다른 두 개의 데이터 센터에서 동시 변경 가능 → 충돌 해결 필요

**협업 편집**

실시간 협업 편집 애플리케이션

사용자가 편집 시 변경 내용을 즉시 로컬 복제 서버에 적용 후 다른 사용자와 서버에 비동기 방식으로 복제

#### 쓰기 충돌 다루기

**동기 대 비동기 충돌 감지**

단일 리더 DB : 첫번째 쓰기가 완료될 때까지 두 번째 쓰기를 차단해 기다리게 함 or 두번째 쓰기 트랜잭션을 중단

다중 리더 DB : 두 쓰기는 모두 성공, 특정 시점에서 비동기로만 감시

**충돌회피**

충돌을 처리하는 제일 간단한 전략<br>많은 다중 리더 복제 구현 사례에서 자주 권장되는 방식

**일관된 상태 수렴**

다중 리더 설정에서는 쓰기 순서가 정해지지 않아 최종 값이 명확하지 않음

⇒ 수렴 방식으로 충돌을 해소 해야 함

수렴 충돌 해소 달성 방법 : UUID, 타임스탬프, 임의 수, 등. 가장 높은 ID를 가진 쓰기를 고름

- 타임스탬프 사용 시 최종 쓰기 승리 → 대중적이지만 데이터 유실 위험이 존재함

#### 리더 없는 복제

다이나모 스타일 (리악, 카산드라…) → 리더의 개념을 버리고 모든 복제 서버가 클라이언트로부터 쓰기를 직접 받을 수 있게 허용

노드가 다운됐을 때 데이터베이스에 쓰기

가정 : 세 개의 복제 서버, 복제 서버 중 하나가 가용 불가 → 리더 기반 설정에서 쓰기 처리를 계속 하려면 장애 복구를 실행해야 함(mongoDB)

리더 없는 설정에서는 장애 복구가 불필요함.

**읽기 복구와 안티 엔트로피**

복제 계획은 모든 데이터가 모든 복제 서버에 복사된 것을 보장해야 한다. 사용 불가능한 노드가 온라인이 된 후 누락된 쓰기는?

- 읽기 복구 - 클라이언트가 여러 노드에서 병렬로 읽기 수행 시 오래된 응답 감지 가능
- 안티 엔트로피 처리 - 백그라운드 프로세스를 두고 복제 서버 간 데이터 차이를 지속적으로 찾아 누락도니 데이터를 하나의 복제 서버에서 다른 서버로 복사한다.

**읽기와 쓰기를 위한 정족수**

세 개의 복제 서버 중 하나만 쓰기를 허용한다면? 어느 범위까지 허용?

쓰기가 세 개의 복제 서버 중 적어도 두 개의 복제 서버에 존재한다는 것을 보장 → 하나의 복제 서버가 오래된 데이터임을 의미, 적어도 하나는 최신값인지 확인 가능

n개의 복제 서버가 있을 때 모든 쓰기는 w개의 노드에서 성공해야 쓰기가 확정, 최소한 r개의 노드에 질의해야 한다. w+r > n이면 읽을 때 최신 값을 얻을 것으로 기대한다.

w와 r의 값이 작을 수록 오래된 값을 읽을 확률이 높음

**최신성 모니터링**

운영 관점에서 데이터베이스가 최신 결과를 반환하는지 여부를 모니터링하는 일은 중요 → 복제가 뒤쳐진다면 원인을 조사할 수 있게 알려줘야 함

복제지연량 = 리더의 현재 위치 - 팔로워의 현재 위치

리더 없는 복제 시스템에서는 쓰기가 적용된 순서 고정 X → 모니터링이 어려움

### 6장 파티셔닝

데이터 셋이 매우 크거나 질의 처리량이 매우 높다면 복제만으로 부족하고 데이터를 파티션으로 쪼갤 필요가 있다. → 이를 `샤딩`

파티션 == 몽고DB의 Shard에 해당함

파티셔닝을 원하는 주된 이유는 확장성. 비공유 클러스터에서 다른 파티션은 다른 노드에 저장될 수 있다.

#### 파티셔닝과 복제

복제와 파티셔닝을 함께 적용 → 각 파티션의 복사본을 여러 노드에 저장함.

각 레코드는 정확히 한 파티션에 속하더라도, 여러 다른 노드에 저장해서 내결함성을 보장

한 노드에 여러 파티션을 저장하는 것도 가능

#### 키 값 데이터 파티셔닝

어떤 레코드를 어느 노드에 저장해야 하나

**파티셔닝의 목적은 데이터와 질의 부하를 노드 사이에 고르게 분산하는 것**

특정 파티션이 질의를 많이 받거나 데이터 양이 많다면 쏠림 → 파티셔닝 효과가 매우 떨어진다.

- 핫스팟

불균형하게 부하가 높은 파티션을 핫스팟이라고 한다.

핫스팟을 피하는 방법 : 레코드를 할당할 노드를 무작위로 선택 : 읽을 때 어디에 저장했는지 알 수 없으니 병렬적으로 질의를 해야 함

**키 범위 기준 파티셔닝**

각 파티션에 연속도니 범위의  키를 할당. (예를 들어 A-B, C-D …..)

단점 : 핫스팟을 유발, 타임스탬프도 마찬가지

**키의 해시값 기준 파티셔닝**

키의 핫스팟의 위험 때문에 많은 분산 데이터스토어는 키 값으로 해시 함수를 사용

좋은 해시 함수는 균일하게 분산되도록 한다.

**쏠린 작업부하와 핫스팟 완화**

키를 해싱해서 파티션을 정하면 핫스팟을 줄이는데 도움이 됨

현재 데이터 시스템은 쏠린 작업부하를 보정x → 애플리케이션 단에서 해결해야 함

가장 간단한 해결책은 각 키의 시작이나 끝에 숫자를 붙이는 것.

#### 파티셔닝과 보조 색인

보조색인 - 레코드를 유일하게 식별하는 용도가 아니라, 특정한 값이 발생한 항목을 검색하는 수단

보조 색인은 데이터 모델링에 매우 유용하다. → 엘라스틱서치 같은 검색 서버에는 존재의 이유

문제점 : 파티션에 깔끔하게 대응되지 않는 문제점

**문서 기준 보조 색인 파티셔닝**

각 파티션은 자신의 보조 색인을 유지하며, 그 파티션에 속하는 문서만 담당한다.

DB CRUD 작업을 할 때는 해당 문서 ID를 포함하는 파티션만 다루면 된다. → 문서 파티셔닝 indexing은 전역 색인, 지역색인이라고 함.

파티셔닝된 DB에 질의를 보내는 방법 : Scatter/Gather

보조 색인을 써서 읽는 질의는 큰 비용이 들 수 있음, MongoDB 문서 기준으로 파티셔닝된 보조 색인을 사용함

#### 파티션 재균형화

- 질의 처리량이 증가해서 CPU를 더 추가하고 싶다.
- 데이터 셋 크기 증가로 디스크와 램을 추가하고 싶다.
- 장비에 장애가 발생해서 그 장비가 담당하던 역할을 다른 장비가 넘겨받아야 한다.

→ 요구사항

- 재균형화 후 부하가 클러스터 내에 있는 노드들 사이에 균등하게 분배
- 재균형화 도중에도 읽기/쓰기 요청은 받아들여저야 함
- 재균형화가 빨리 실행되고, 네트워크와 디스크 I/O 부하를 최소화할 수 있도록 노드들 사이에 데이터가 필요 이상으로 옮겨져서는 안된다.!!
