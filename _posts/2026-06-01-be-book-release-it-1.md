## 🎯 1단계: 진입 전 준비 (2~3분)

**👁️ 이 챕터에서 다룰 내용을 예측하면?**

운영 환경에서의 장애 사례와 이를 방지하기 위한 아키텍처 설계 원칙, 안정성 패턴들을 다룰 것으로 예상

**🧠 내가 이미 알고 있는 것은?**

서킷브레이커, 타임아웃, 재시도 전략 등 기본적인 안정성 패턴의 존재는 알고 있음. 하지만 실제 장애 사례 기반으로 왜 필요한지 깊이 이해하지는 못한 상태

## 📖 2단계: 독서 중 포착 (능동적 독서)

### 1장 - 운영환경의 현실

**💡 핵심 개념 / 코어 키워드**

- 설계·아키텍처 결정 = 재무적 결정 → 기술적 관점과 재무적 관점을 함께 봐야 한다
- 실용주의 아키텍트는 메모리 / CPU / 대역폭 / 하이퍼스레딩 / CPU 바인딩의 장단점을 논의한다

---

### 2장 - 항공사를 멈추게 한 예외

**💡 핵심 개념 / 코어 키워드**

- Statement close 시 예외 발생 → 연결이 닫히지 않아 자원 누수
- 호출 40번 → 커넥션 풀 고갈 → `connectionPool.getConnection()` 에서 모든 호출 블록 → 단일 CF 장애
- **어떠한 경우라도 서비스 복원이 최우선** (조사보다 먼저)

**❓ 핵심 질문**

- 한 시스템의 버그가 다른 시스템에 영향을 미치지 않게 하는 방법은?

---

### 3장 - 안정성 정의와 균열

**💡 핵심 개념 / 코어 키워드**

- 안정성의 정의: 일시적 충격, 영구적 스트레스, 구성요소 장애가 발생하더라도 계속 트랜잭션을 처리하는 시스템
- 장애 주요 원인: **메모리 누수**, **데이터 증가**
- 강한 결합은 균열을 가속화한다
- 장애는 신속하게 전파된다 → 충분히 방어적으로 작성하지 않으면 연계 장애로 번짐

---

### 4장 - 안정성 안티패턴

**💡 핵심 개념 / 코어 키워드**

- **통합 지점 장애 대응**: Circuit Breaker, Decoupling Middleware가 가장 효과적
- **연쇄 반응**: 대부분 애플리케이션 메모리 누수 시 발생 → 오토스케일링으로 대응
- **사용자 특성**: 메모리를 소비함 / 예측 불가 행동 / 악의적 사용자 / 대규모 유입 가능
- **동시성 문제 방지 (CQRS)**: 도메인 객체를 불변으로 만들면 동기화 불필요. 상태 변경 시 명령 객체 생성
- **캐시**: 메모리 사용량은 실행 환경에서 설정 가능해야 함
- **공유 자원 주의**: 병목, 처리 능력 제한, 안정성 위협 가능
- **도그파일(Dogpile): 순간적 부하 집중 현상**
  - **크론 작업 집중**, 다수 서버 동시 재시작, 구성관리 시스템 변경 푸시 시 발생
  - 시간 시차를 두어 수요 분산 (예: 크론 작업을 정시/자정으로 설정하지 않기)
  - 재시도 간격을 점차 늘려 펄스 방지
- **응답 지연**: 연계 장애 유발. CPU 사용률이 높다면 트랜잭션이 아닌 GC 처리 때문일 수 있음
- **현실적인 데이터 양 사용**: 쿼리에 LIMIT, Pagination 적용 / 타 서비스 호출 시 프로토콜 제한 설정

**❓ 이해되지 않은 부분 / 더 찾아볼 것**

- 인프라 관리 도구의 제한기와 보호 장치 구체적 구현 방법

---

### 5장 - 안정성 패턴

**💡 핵심 개념 / 코어 키워드**

**[시간제한 - Timeout]**

- 통합 지점, 블록된 스레드, 응답 지연에 시간 제한 적용 → 스레드 블록 방지 → 연계 장애 방지
- 지연 재시도 고려: 즉각 재시도 시 또 다른 타임아웃 발생 가능 → 작업을 대기열에 넣고 재시도

**[회로 차단기 - Circuit Breaker]**

- 폐쇄 상태: 정상 작동. 실패 횟수가 임곗값 초과 시 → 개방
- 반개방: 일정 시간 후 성공 가능성 판단. 실패 시 다시 개방
- Fallback 전략: 마지막 정상 응답 또는 캐시 값 반환
- 서킷브레이커 상태는 운영 조직에서 모니터링 가능해야 함 (Droppable 프로젝트에 필요)
- 논의사항: 재고 확인 불가 시 주문 수락 여부? 신용카드/주소 확인 불가 시 처리 방법?

**[격벽 - Bulkhead]**

- 한쪽 침수 시 전체 침몰 방지 → 구획 분리
- 클라우드: AWS Zone / Region 분리
- 분할 수준: 스레드 풀 / 서버 CPU / 클러스터 서버
- MSA에서 장애는 급작스럽게 전파 → 격벽 설치 권장

**[데이터 정리]**

- DB, 로그 파일(파일 시스템 90~95% 시 입출력 오류 시작), 메모리 캐시 모두 정리 필요
- 캐시 제한 필수: 키 공간이 유한한지 / 캐시 항목이 변경되는지 고려

**[빠른 실패 - Fail Fast]**

- 느린 실패 응답이 최악. SLA 준수 불가 시 즉시 알리기
- 자원 예약 전에 기본 입력값 유효성 검사 먼저
- DB 연결 확인 후 도메인 객체 가져오는 순서 지키기

**[파손 방치 - Let It Crash]**

- 크기 제한 / 교체 속도(가능한 빨리 재시작) / 감독 / 재통합
- 모노리스는 파손 방치에 적합하지 않음 (시작 시간이 긴 대규모 프로세스)

**[핸드셰이킹]**

- 서버가 작업 부하를 스스로 조절해 자기 보호
  - rate limiter
- HTTP는 핸드셰이킹에 적합하지 않음
- 회로 차단기 = 핸드셰이킹 불가 서비스 호출 시 임시방편

**[테스트 하네스]**

- 통합 지점 상대편에서 원격 시스템을 모방
- 좋은 테스트 하네스는 악독해야 함: 느린 응답 / 무응답 / 쓰레기 응답 시뮬레이션 가능

**[결합 분리 미들웨어]**

- 시스템을 통합하면서 결합을 분리
- 아키텍처 결정은 빠르게: 나중에 되돌릴 수 없음
- 전체 결합 분리로 많은 장애 모드 회피 가능

**[부하 제한 / 배압 / 조속기]**

- 부하 제한: 수평 확장 불가 시 503으로 응답
- 배압: 소비 측 속도를 늦춰 안전 확보. 대기열이 유한해야 응답 시간도 유한
- 조속기: 자동규모조정이 예산을 초과하지 않도록 개입 가능한 속도 제어

**🔖 좋은 문장 / 인사이트**

> 어떠한 경우라도 서비스 복원이 최우선이다 (조사보다도)

> 안정성이란 일시적인 충격, 영구적인 스트레스, 구성요소의 장애가 발생하더라도 계속 트랜잭션을 처리하는 시스템이다

> 느린 실패 응답이 최악이다

## 🔄 3단계: 내 언어로 설명하기 (Feynman 기법)

**👶 신입 개발자에게 이 챕터를 설명한다면?**

시스템은 언제든 장애가 난다. 중요한 건 한 곳의 문제가 전체로 번지지 않게 막는 것이다. 커넥션 풀 하나가 고갈되면 거기에 의존하는 모든 기능이 멈출 수 있다. 그래서 타임아웃, 서킷브레이커, 격벽 같은 패턴으로 장애를 격리하고, 빠르게 실패를 알려서 연쇄 장애를 막는 것이 안정적인 시스템의 핵심이다.

## 🔗 4단계: 연결 & 적용

**🛠️ 현재 프로젝트/실무에 적용할 수 있는 포인트**

- Droppable 프로젝트: 서킷브레이커 상태 모니터링 엔드포인트 추가 필요
- 크론 작업 시간 분산: 정시/자정 설정 지양, 시차 두기
- 타 서비스 API 호출 시 반드시 타임아웃 설정
- 쿼리에 LIMIT / Pagination 적용 확인
- 캐시 최대 메모리 제한 설정 여부 확인

**🧱 기존에 배운 개념과 연결되는 점**

- CQRS 패턴과 동시성 문제 방지의 연결
- MSA 환경에서 격벽(Bulkhead) = 서비스 간 독립성 확보
- Gradle `implementation` vs `api` 스코프 — 결합을 최소화하는 철학과 동일 (내부 구현은 숨기고, 진짜 공개 API만 노출)

**🔍 기존 코드에서 개선할 수 있는 부분**

- 외부 API 호출부에 타임아웃 / 서킷브레이커 적용 여부 검토
- DB 쿼리 중 LIMIT 없는 전체 조회 쿼리 점검
- 로그 파일 로테이션 정책 설정 여부 확인

**🤔 이 챕터에서 스스로에게 던질 질문 3가지**

3. 격벽(Bulkhead) 패턴을 MSA 환경에서 적용할 수 있는 구체적인 수준 세 가지는?
