# 리소스 로딩 순서 최적화

최적화가 잘 된 웹페이지는 로드될 때 중요한 컴포넌트와 리소스를 사용할 수 있게 준비하여 부드러운 사용자 경험을 제공한다. 이는 사용자에게 애플리케이션 성능이 좋다는 인식을 주고, Core Web Vitals에 좋은 점수로 이어진다.

앱의 성능을 측정하기 위한 FCP(First Content Paint), LCP(Large Contentful Paint), FID(First Input Delay) 등의 주요 성능 지표들은 주요 리소스의 로딩 순서에 직접적인 영향을 받는다. (예) LCP의 경우 `hero image`가 로드되지 않으면 계속 늘어진다.)

## 리소스 로딩 순서 최적화

### 리소스 순서 처리

Web Vitals를 최적화하기 위해서 각 성능 지표들이 의미하는 바를 이해하고, 각 지표와 연관된 리소스들이 어떤 관계를 갖는지 이해해야 한다. 지표 중 FCP, LCP, FID는 나열된 순서대로 측정되므로, 각 지표 달성을 위한 리소스들 역시 순서대로 제공되어야 한다.

예시 :

FCP 측정 시 LCP가 측정되기 위해 hero image가 사용가능하도록 준비되어야 한다.

LCP 측정 시 페이지 상호작용이 가능해야 하기에 FID 자바스크립트들이 모두 다운로드되고 분석 준비가 되어야 한다.

### 네트워크/CPU 활용성

리소스들이 네트워크나 CPU가 적절히 활용되도록 파이프라이닝 되지 않는다. 그결과 네트워크 처리 과정에서는 CPU가 놀고, CPU가 처리중일 때 네트워크가 노는 Dead Time이 발생하게 된다.

예시 : 스크립트들의 다운로드가 동시적으로 이루어질 때 순차적으로 이루어질 때

스크립트의 다운로드에 네트워크 대역폭이 “동일하게 나눠 처리”될 경우 모든 스크립트들이 다운로드되는 시간은 동시적이나 순차적이나 동일할 것이다. 다만 동시적으로 다운로드할 경우 다운로드가 진행되는 동안 CPU는 놀고 있을 것이다.

그러나 스크립트를 순차적으로 동시에 다운로드할 경우 CPU는 먼저 받은 스크립트를 즉시 처리할 수 있게 된다. 이로 인해 CPU와 네트워크를 조금 더 활용할 수 있게 된다.

### 서드파티 패키지

웹사이트에 기능을 제공하기 위해 3P 라이브러리가 자주 쓰인다. 서드파티 라이브러리들은 자체적인 JS, 이미지, 폰트 등과 같은 리소스를 포함하고 있다.

3P는 이를 사용하는 웹사이트들의 로딩 성능을 최적화를 지원할 의무는 없기 때문에, 무거운 자바스크립트를 실행해 상호작용이 가능해지는 시간까지 시간을 지연시키거나, 다른 중요 리소스들의 다운로드를 방해할 수 있다.

3P들이 앱의 성능에 미치는 영향보다 제공되는 기능에 더 초점을 맞춰 사용여부를 결정하는 경향이 잉ㅆ는데, 이 것들이 쌓이면 나중에 컨트롤하기 어려워진다.

### 플랫폼별 특이사항들

각 브라우저들은 요청의 우선순위 처리 및 관련 힌트 처리의 구현이 다를 수 있다. 특정 브라우저의 동작이 다른 경우 리소스 로딩 순서를 일관되도록 맞추는 것이 어려워진다.

예시) 크로미움 플랫폼의 preload 버그 : preload 지시자를 사용하면 브라우저에게 중요 리소스들을 가능한 빨리 다운받을 수 있도록 한다. 다만 해당 리소스가 현재 페이지에서 사용될 것이 확실할 때에만 사용해야 한다. 크로미움 버그는 preload로 지정된 리소스들이 다른 높은 우선순위로 설정된 리소스보다도 먼저 요청되는 문제였는데, 최적화 계획을 세우는데 걸림돌이 된다.

### HTTP2의 우선순위 처리

HTTP2 프로토콜은 자체적으로 리소스들의 우선순위나 순서를 설정하기 위한 옵션을 제공하지 않고 있다. 우선순위 지정을 위한 기능들을 사용할 수 있게 되더라도, HTTP2의 리소스 우선순위 처리 기능 자체가 처리하기 어려운 근본적인 문제를 가지고 있다. 애초에 서버나 CDN들은 개별 요청에 순서라는 것을 추측할 수 없는데, 일부 CDN들은 우선순위를 재지정하기도 하고, 다른 CDN을 부분적으로 구현했거나, 결함이 있다거나, 애초에 우선순위를 구현하지 않는 경우이다.

### 리소스 별 최적화

리소스 순서를 최적화하려면 서빙되는 리소스 자체도 최적으로 제공되어 빠르게 로드되도록 해야 한다. 중요한 CSS는 인라인되어야 하며, 이미지는 적절한 사이즈로 리사이즈되어야 하고, JS는 `코드 스플리팅`이 적용되어 점진적으로 클라이언트에 전달되어야 한다.

**프레임워크 적용**

프레임워크 자체적으로 JS와 데이터를 코드 스필리팅하여 점진적으로 서빙하는 기능이 부족하다. 개발자는 개발한 코드들을 여러 청크로 나누기 위해 아래 기능들에 의존해야 한다.

1. React → Suspsnse, Concurrent(↔ Parallel) Mode, Data Fetching
2. dynamic import를 통한 지연 로딩 : 코드를 나눌 경계를 개발자가 직접 찾아 적용해야 한다.

**코드 스플리팅**

코드 스플리팅도 너무 과하지 않게 적용하여 성능을 떨어트리지 않도록 균형을 찾아야 한다. 가급적 작게 나누는 것이 유리하다. 그 이유는

1. 각 라우팅과 상호작용 시 받게 되는 JS를 최소화한다.
2. 일반적인 의존에 대해서 캐싱할 수 있도록 한다. → 따라서 라이브러리의 변경이 모든 번들의 재다운로드를 유발하지 않게 한다.

주의점 : 너무 JS를 잘게 나눌 경우 코드 조각들이 낮은 압축률을 갖게 되므로 브라우저의 성능에 영향을 미칠 수 있다.

**Dead Code 제거**

리소스 최적화에는 사용하지 않는 dead code를 제거하는 것도 중요하다. 필요없거나 고립된 JS들이 종종 클라이언트 측에 전송되어 성능에 부정적인 영향을 미친다. 라이브러리 혹은 npm 패키지가 esmodule로 번들되어있지 않다면 tree shake등의 최적화를 적용할 때 제약이 생긴다.

## 각 리소스들에 대한 관계, 제약사항 및 우선순위들

해당 주제는 리소스 로드 순서를 정의하기 전에 고려해야 할 리소스 별 권장사항, 제약사항 및 기타 사항들이다.

### 중요 CSS

**중요 CSS는 FCP에 필요한 최소 CSS를 의미한다**.

이런 CSS들은 별도의 파일로 포함되는 것보다 HTML파일에 인라인으로 포함되는 것이 좋다. 해당 라우팅 경로에 필요한 CSS에 대해 주어진 시간 안에 다운로드되어야 하며, 중요 CSS들은 모두 올바르게 분기되어야 한다.

인라인이 불가능한 경우 중요 CSS들은 문서 다운로드와 동시에 preload되어 서빙되게 할 수 있다. 여러 도메인에서 중요 CSS들을 서빙하거나 구글 폰트와 같은 서드파티 CSS를 직접 사용하지 않도록 해야 한다. 만약 지연이 생길 경우 FCP와 LCP에 영향이 미칠 수 있다.

```javascript
// 사용 X : FCP 지연
<link href="https://fonts.googleapis.com/css2?family=Roboto&display=swap" rel="stylesheet">
// 1. fonts.googleapis.com로 DNS 조회
// 2. TLS(HTTPS) 연결
// 3. CSS 파일 다운로드
// 4. CSS 내부의 @font-face에서 다른 도메인(fonts.gstatic.com)으로 폰트 파일을 다시 요청
// 5. 또 다른 DNS + TLS + 다운로드
```

결론 : 1. 인라이닝되지 않은 CSS들은 우선순위가 부여되어야 하며, First 파티 JS, ATF 이미지(스크롤하지 않아도 보여야 하는 이미지들)보다 먼저 로드되도록 해야 한다. 2. CSS 인라이닝도 너무 과할 경우 HTML 자체의 볼륨이 커지기에 메인 쓰레드에서 스타일을 파싱하는데 오랜 시간이 걸린다.

### 폰트

중요 CSS와 동일하게 [**중요 폰트**](https://web.dev/font-best-practices/)를 위한 CSS역시 인라인처리 되어야 한다.

인라이닝이 어려울 경우 스크립트는 [**preconnect**](https://web.dev/uses-rel-preconnect/)처리되어 로드되어야 한다. 구글 폰트와 같은 외부 도메인에서 로드하여 지연이 발생하는 경우 FCP에 악영향을 미친다.

### ATF(Above the Fold) 이미지들

ATF 이미지는 뷰포트 내에 존재하여 페이지 로드 시 사용자에게 처음 표시되는 이미지를 뜻한다. hero image가 예시이다.

모든 ATF 이미지는 크기가 명시되어야 하며, 그렇지 않으면 레이아웃의 변경이 일어나 CLS에 악영향을 준다. 참고로 hero image의 로딩이 지연되거나 빈 placeholder영역은 LCP를 지연시킨다.

### **BTF(Below the Fold) 이미지들**

페이지 로드 직후 뷰포트에 보여지지 않는 이미지들을 의미한다. 따라서 이 이미지들은 lazy loading 적용 대상이다. lazy loading을 적용하여 1P JS나 중요한 3P 스크립트가 로드되는 것을 방해하지 않도록 한다.

### 1P JS

1P JS는 앱의 상호작용이 준비되는 것에 관련되어있다. 1P JS는 이미지나 3P JS에게 우선순위에 밀려 늦게 로드되거나, 3P JS보다 늦게 메인 스레드에서 처리될 수도 있다. 따라서 미리 로드되어야 하며, 3P JS보다 먼저 메인쓰레드에서 실행되어야 한다.

참고 : 서버 렌더링 환경에서 1P JS는 FCP나 LCP 자체를 방해하지 않는다.

### 3P JS

HTML의 **`<head>`** 에 동기적으로 포함된 3P스크립트는 CSS 및 폰트 파싱을 블록하여 FCP에 악영향을 준다. 또한 동기적으로 포함된 스크립트는 HTML 본문의 파싱을 지연시킨다. 메인 쓰레드에서 실행되는 3P 스크립트는 1P 스크립트의 실행을 지연시키고, hydration도 지연시켜 FID를 지연시킨다.
