## 🎯 1단계: 진입 전 준비

**👁️ 이 챕터에서 다룰 내용을 예측하면?**

아키텍처 선택의 기준과 스타일들을 설명할 것 같다. 모놀리스와 MSA를 어떻게 구분하고 결정할지에 대한 실질적인 기초를 다룰 것.

**🧠 내가 이미 알고 있는 것은?**

- 모놀리스 = 하나의 배포 단위, MSA = 독립 배포 가능한 작은 서비스들
- 계층형 아키텍처(Layered): Controller → Service → Repository 구조
- 쿠버네티스로 컨테이너 오케스트레이션 경험 있음

---

## 📖 2단계: 독서 중 포착

**💡 핵심 개념**

- **소프트웨어 아키텍처 정의** — 시스템의 구조를 결정하는 설계 결정의 집합
- **아키텍처 스타일 / 패턴 / 결정 동인** — 환경에 적합한 단 하나의 정답 스타일은 없다. 상황에 따라 선택해야 한다.
- **`헥사고날 아키텍처`** — 계층형 아키텍처의 관심사 분리 장점 + 포트/어댑터 패턴을 통한 느슨한 결합. 외부 시스템(DB, API 등)과의 의존성을 인터페이스(포트)로 격리한다.
- **모듈화** — REST PUT(전체 엔티티 상태 교체) vs PATCH(부분 수정)로 경계를 명확히 한다.
- **품질 속성** — 보안, 개인정보보호, 성능, 확장성, 복원성, 복잡성

**🔖 확장성 핵심 비교**

| 구분 | 모놀리스 | 마이크로서비스 |
| --- | --- | --- |
| 확장 단위 | 전체 인스턴스 통째로 | 리소스 집약적인 서비스만 독립 확장 |
| 리소스 할당 | 가장 무거운 기능 기준으로 전체 할당 | 필요한 부분에만 리소스 집중 |
| 결함 격리 | 어렵다 (모듈화해도 한계) | 서비스 단위로 격리 가능 |
| 오버헤드 | 낮음 | 컨테이너 + 오케스트레이션 오버헤드 있음 |

**❓ 더 찾아볼 것**

- 헥사고날 아키텍처의 포트/어댑터 패턴 — 실제 Spring 코드에서 어떻게 구현되나?
- 모듈화된 모놀리스와 MSA의 결함 격리 차이가 실제 장애 상황에서 어떻게 다르게 나타나는가?

**🔖 인상 깊었던 문장**

> *"모듈화된 모놀리스는 많은 이점을 제공하지만 마이크로서비스와 달리 결함에 대한 격리를 쉽게 보장할 수 없다."*

## 🔄 3단계: 내 언어로 설명하기 (Feynman)

> 책을 덮고 신입 개발자에게 설명한다고 생각하기

**헥사고날 아키텍처를 쉽게 설명하면?**

계층형 아키텍처(Controller-Service-Repository)는 코드가 위에서 아래로만 흐르지만, 상위 레이어가 하위 레이어에 직접 의존해서 DB나 외부 API를 바꾸면 코드도 바꿔야 한다. 헥사고날은 이 문제를 "포트(인터페이스)"로 해결한다. 비즈니스 로직(안쪽)은 포트만 바라보고, 실제 DB나 외부 API(바깥쪽)는 어댑터로 포트를 구현한다. 덕분에 DB를 MySQL에서 MongoDB로 바꿔도 비즈니스 로직은 손대지 않아도 된다.

**모놀리스 확장 비효율을 한 문장으로?**

모놀리스는 특정 기능 하나가 많은 리소스를 써도 시스템 전체를 통째로 복사해야 하므로, 필요 없는 기능들도 함께 스케일 아웃되어 리소스가 낭비된다. ⇒ 전략적 모놀리스 필요

## 🔗 4단계: 연결 & 적용

**🛠️ W사 프로젝트 실무 연결**

현재 W사 프로젝트가 **모놀리식 구조인데 쿠버네티스에서 운영**되고 있다. 이것이 이 챕터에서 말하는 비효율의 실제 사례다.

- 특정 기능(예: 검색, 대용량 조회)에 트래픽이 몰려도 → **해당 모듈만 확장 불가**
- 전체 인스턴스를 복제해야 하므로 → **메모리, CPU가 가장 무거운 기능 기준으로 낭비됨**
- 반면 MSA였다면 검색 서비스만 Pod를 늘리면 끝

**🧱 기존 지식과 연결**

- HikariCP 커넥션 풀 설정을 인스턴스별로 잡는 이유 → 모놀리스 스케일 아웃 시 전체 복제되므로 DB 커넥션 수 계산이 중요해짐 (이전 학습한 `maximum-pool-size` 설정과 직결)
- `@Async` + 쓰레드 분리 → 모놀리스 내에서 일부 기능을 비동기로 분리하는 것이 결함 격리의 차선책

**🔍 코드/설계에서 개선 고려 포인트**

- W사에서 리소스 집약적인 기능(대용량 조회, 배치 등)을 모듈 경계로 명확히 나눠두면, 나중에 MSA 전환 시 분리 비용을 줄일 수 있다
- 현재 계층형 아키텍처에서 헥사고날로 전환 시 — Repository 인터페이스를 포트로 취급하고 있다면 이미 절반은 된 셈
