웹에 컨텐츠를 표현하는 방법은 다양하다. 어떻게/어디서 데이터를 받아오고, 컨텐츠 렌더링을 하는지 결정하는 것은 앱의 성능을 좌우하는 포인트이다.

CSR, SSR, Hydration, 점진적 렌더링, Static 렌더링 등 다른 방법을 사용하기 위한 프레임워크 혹은 라이브러리들이 사용된다. → 각 패턴의 영향과 결과를 이해하는 것은 앱에 적합한 방식을 찾기 위해 꼭 필요하다.

크롬 팀은 `Rehydration` 접근 방식 보다 정적 렌더링이나 서버사이드 렌더링을 고려하도록 권장했다. 지난시간 동안 현대의 프레임워크는 `점진적 로딩`과 여러 렌더링 기법을 기본으로 구현하였고, 좋은 성능과 새 기술의 적용 모두 고루고루 발전하였다.

**용어**

`Hydration` : SSR된 HTML을 브라우저에서 JavaScript로 다시 활성화하는 과정

- 서버에서 HTML을 보내면 브라우저가 렌더링하여 사용자에게 보여주는데, 인터렉션은 동작하지 않음 → HTML에 JS를 붙여서 동작하도록 만드는 작업이다.

`Rehydration` : Hydration의 구체적인 구현 패턴 중 하나

- Hydration : 서버에서 렌더링된 정적 HTML을 브라우저에서 활성화시키는 전체적인 과정
- Rehydration : 서버에서 렌더링된 상태와 클라이언트에서 렌더링될 상태가 불일치할 때 이를 맞추는 과정을 강조할 때 쓰는 방법
- Next.js SSR + hydration 사용하는 경우 → hydration mismatch 경고 : 클라이언트가 rehydration을 시도하면서 HTML과 상태를 동기화하는 것

`점진적 로딩` : 앱의 초기 로딩 속도를 빠르게 하기 위해 페이지를 여러 단계로 나누어 필요한 부분만 우선 로딩하는 기법 (중요한 부분만 먼저 로딩)

**스트리밍 렌더링** : 서버가 HTML을 한꺼번에 다 만드는게 아닌 `Chunk` 단위로 조금씩 보내서 브라우저가 받는 즉시 렌더링

이렇게 하면 사용자 입장에서는 화면이 빠르게 보이고, 나머지가 채워짐

**점진적 로딩과 `스트리밍`** : 최근 프레임워크는 HTML 스트리밍을 지원하면서 점진적 로딩과 스트리밍이 엮여서 나옴.

### 짧은 웹 렌더링 역사

웹 기술은 앱의 요구사항을 만족하기 위해 끊임없이 발전해왔다.

2000년대 초에서는 서버에 의해 렌더링되는 HTML이 대부분이었다. 개발자들은 HTML 페이지를 렌더링하기 위해 PHP나 ASP같은 서버사이드 스크립팅 언어를 사용해따. 페이지의 탐색은 새로 불러오는 것에 의존했으며, JavaScript는 그 안에서 특정 요소의 노출 여부나 폼의 활성화, 비활성화를 결정하는 정도로만 작게 사용했다.

2006년에 Ajax로 SPA를 개발하는 것이 알려졌고, Gmail이 유명한 예시가 되었다. Ajax는 개발자들에게 페이지들에게 새로 불러오지 않고도 동적으로 요청을 보낼 수 있게 해 주었다. 따라서 SPA는 데스크톱 앱과 유사하게 구현될 수 있었다. → 개발자들은 JavaScript를 이용해서 데이터를 받아오고 화면을 그렸다. JavaScript라이브러리와 프레임워크가 만들어져 MVC 프레임워크의 뷰 레이어를 구현하는데 사용되었다. jQuery, AngularJS와 같은 클라이언트사이드 프레임워크들을 JavaScript 기반 코어 기능들을 쉽게 개발할 수 있게 해주었다.

Reactsms 2013년 SPA와 모바일 웹 기반으로 유저 인터페이스와 UI 컴포넌트를 만들 수 있는 유연한 프레임워크로 소개되었다. 2015년부터 2020년까지 데이터플로우 구조 라이브러리(Redux), CSS 프레임워크, 라우팅 라이브러리, 모바일 앱 프레임워크(React Native)들을 포함해 React의 생태계가 발전했다. 그러나 순수 클라이언트 사이드 측 렌더링의 단점들이 부각되며 개발자는 클라이언트나 서버 양쪽에서 최적의 성능을 내기 위해 다양한 시도들을 하게 되었다.

### 렌더링 - 성능의 주요 지표

위에 이야기한 단점들에 대해 말하기 전에, 각 렌더링 매커니즘의 성능을 어떻게 측정하는지 이애해야 한다.

TTFB_Time To First Byte : 링크 클릭과 해당 사이트의 첫 바이트를 받기 까지 시간

FP_First Paint : 사용자가 어떤 컨텐츠를 보게 되거나 화면에 약간의 픽셀이 그려지기까지의 시간

FCP_First Contentful Paint : 페이지 컨텐츠의 일부가 화면에 렌더링될 때까지의 시간

LCP_Large Contentful Paint : 메인 페이지의 컨텐츠가 보여지기까지의 시간, 뷰포트 내의 큰 이미지, 텍스트가 보여짐을 의미

TTI_Time To Interactive : 페이지에 인터렉션이 가능해지기까지의 시간,

TBT_Total Blocking Time : FCP부터 TTI까지 시간

1. JavaScript 번들 사이즈가 크면 페이지를 로드할 때 FCP와 LCP 시간이 증가하므로, 사용자는 기다려야 하는 시간이 늘어날 것이다.
2. JavaScript 번들 사이즈가 크면 TTI와 TBT에 영향을 주어 이벤트 바인딩이 될 때까지 아무 인터렉션을 하지 못할 것이다.
3. TTFB는 사용자의 요청을 처리하는 서버의 속도와 관련이 있다.
4. preload, prefetch, script 속성 처리와 같은 테크닉들은 브라우저가 그들을 어떻게 해석하느냐에 따라 파라미터들을 다르게 변화시킨다. → 우선순의를 어떻게 부여하는지 확인
