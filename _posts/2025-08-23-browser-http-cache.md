웹사이트와 애플리케이션 성능은 이전에 가져온 리소스를 재사용함으로써 향상할 수 있다. Latency, 트래픽을 줄여주기에 리소스를 보여주는데 필요한 시간을 줄여준다.

## 웹 캐시

클라이언트는 HTTP 요청을 통해 필요한 데이터(HTML, CSS, JS, 이미지 등)을 불러온다. 기본적으로 웹사이트가 실행될 때마다, 클라이언트는 해당 웹사이트를 그리기 위해 필요한 데이터 전부를 다 불러와야 한다.

HTTP 캐시를 효율적으로 관리하려면 Cache-Control 헤더를 섬세하게 조절해야 한다. Cache-Control 헤더에 따라 받은 리소스의 생명 주기가 결정된다.

## 여러 종류의 캐시들

캐싱 : 주어진 리소스의 복사본을 저장하고 있다가 요청 시 제공하는 기술

- 서버 부하를 완화
- 클라이언트에 더 가까이 존재하므로 성능이 향상됨

모든 리소스가 영원한 것은 아니므로, 리소스가 변하기 전까지 캐싱하고, 이후에는 캐싱하지 않아야 한다.

리소스 : HTTP에서 리소스란 웹브라우저가 가져올 수 있는 모든 종류의 파일을 말한다. HTML, CSS, JS, 이미지, 비디오 파일 등이 해당된다.

- 캐시의 종류

  크게 Private(사설)과 Shared(공유)캐시로 구분할 수 있다.

  Shared 캐시는 한 명 이상의 사용자가 재사용할 수 있도록 응답을 저장하는 캐시이다. Private 캐시는 한 명의 사용자만 사용하는 캐시를 말한다.

### 1. Private 브라우저 캐시

사설 캐시는 단일 사용자가 전용으로 사용한다.

브라우저 캐시는 그 사용자에 의하여 HTTP를 통해 다운로드한 모든 문서를 가지고 있는데, 이 캐시는 추가적인 요청없이 뒤로가기, 앞으로가기, 저장, 소스로 보기 등을 위해 방문했던 문서들을 사용할 수 있도록 해준다. 오프라인 브라우징을 개선한다.

해당 브라우저 캐시는 HTTP 요청을 하는 클라이언트 애플리케이션에 의해 내부 디스크에 이뤄지는 캐시이며, HTTP 캐시라고 불리기도 한다.

브라우저에서 캐싱을 처리하는 속성은 여러가지가 있는데, ETag, Cache-Control이 있다.

### 2. Shared 프록시 캐시

공유 캐시는 한 명 이상의 사용자에 의해 재사용되는 응답을 저장하는 캐시이다.

예를 들어 ISP는 많은 사용자들을 서비스하기 위해 지역 네트워크 기반의 웹 프록시를 설치했다면, 조회가 많이 되는 리소스는 재사용되어 네트워크 트래픽과 레이턴시를 줄여준다.

### ETags (Entity Tags)

웹캐시에서 사용되는 HTTP 헤더 중 하나로, 클라이언트가 받은 리소스(HTML, JSON, 이미지 등)의 버전을 식별할 수 있게 한다. 이를 통해 효율적인 캐싱과 불필요한 데이터 전송 방지를 가능하게 한다.

1. 서버는 리소스를 응답할 때 ETag 헤더를 추가해 리소스의 고유한 식별자를 제공한다.
2. 클라이언트는 ETag값을 저장해두고, If-None-Match 헤더에 넣어서 보낸다.
3. 서버는 클라이언트가 보낸 ETag 값과 현재 리소스의 ETag를 비교해 변경 여부를 판단한다.

## 캐싱 동작의 대상

HTTP는 일반적으로 `GET` 메서드에 대한 응답을 캐싱한다. 기본 캐시 키(Primary Cache Key)는 요청 메서드, 대상 URI로 구성된다. 일반적인 캐싱 엔트리의 형태는 다음과 같다.

- 검색 요청의 성공적 결과 : HTML문서, 이미지 등의 리소스를 포함하는 GET 요청에 대한 응답 _ 200 OK
- 영구적인 리다이렉트 : 301
- 오류 응답 : 404 _ Not Found
- 완전하지 않은 결과 : 206 응답

## 캐싱 제어

### Cache-Control 헤더

HTTP/1.1 기본 헤더 필드는 요청/응답 양측 모두에 존재해, 캐싱 매커니즘을 위한 디렉티브를 지정하는데 사용된다.

### 1. Cache-Control: no-store

클라이언트 요청, 서버 응답에 관해서 어떤 것도 저장하지 않는다. 요청이 서버측으로 전송되고 전체 응답은 매번 다운로드 된다. 캐시를 쓰지 않는다는 말에 더 가까운 속성이다.

### 2. Cache-Control: no-cache

캐시된 복사본을 사용자에게 릴리즈하기 전에, 유효성 확인을 위해 원 서버로 요청을 보낸다. 값은 대부분의 브라우저에서 max-age=0 과 동일한 뜻을 가진다. (캐시를 저장하지만, 사용하려 할 때마다 서버에 재검증 요청을 보낸다.)

### 3. 사설 캐시와 공개 캐시

CDN과 같은 중간 서버가 특정 리소스를 캐시할 수 있는지 여부를 지정하기 위해 Cache-Control 헤더 값으로 public 또는 private를 설정할 수 있다.

- Cache-Control: Private

  응답이 단일 사용자만을 위한 것이며, 공유 캐시에 의해 저장되어서는 안된다는 것을 가리킨다.

- Cache-Control: Public

  응답이 어떤 캐시에 의해서든 캐시되어도 좋다는 의미이다. (모든 사람, 중간 서버가 캐시를 저장할 수 있음)

  HTTP 인증, 보통 캐시 가능하지 않은 응답 상태 코드를 지닌 페이지가 캐시되어야 할 경우 유용할 수 있다.

  예) Cache-Control: public, max-age=86400

### 4. Cache-Control: max-age=`<Second>`

```javascript
Cache-Control: max-age=31536000
```

`max-age=<seconds>`

리소스가 유효하다고 판단되는 최대 시간이다. 이 디렉티브는 요청 시간에 상대적이며, `Expires` 헤더가 설정되어있더라도 그 보다 우선된다.

한 번 받아온 리소스의 유효기간이 지나기 전이라면, 브라우저는 서버에 요청을 보내지 않고 디스크 또는 메모리에서만 캐시를 읽어와 계속 사용한다.

![](/assets/img/2025-08-23/browser-http-cache-1.png)

JavaScript 파일을 요청하는 경우 Cache-Control 헤더 값은 max-age=31536000 (60 * 60 * 24 * 365)이기 때문에 1년동안 캐시할 수 있다. 메모리에서 유효한 캐시가 있기에 `from memory cache` 로 표기된 것을 확인할 수 있다.

### 5. Cache-Control: must-revalidate

해당 디렉티브 사용 시 오래된 리소스를 사용하기 전에 그 상태를 확인하고, 만료된 리소스는 사용하지 말아야 한다. 캐시는 유효 기간이 지나면 완전히 사라지는 대신 조건부 요청을 통해 캐시가 유효한지 재검증을 수행한다.

![](/assets/img/2025-08-23/browser-http-cache-2.png)

재검증 결과 브라우저가 가지고 있는 캐시가 유효하다면 `304 Not Modified` 요청을 내려준다. 304 Not Modified 응답은 HTTP 본문을 포함하지 않기 때문에 매우 빠르게 내려받을 수 있다.

스크린샷에는 59.1KB의 리소스 캐시 검증을 위해 304바이트만의 네트워크 송수신만 주고받았다.

**If-None-Match와 If-Modified-Since가 포함된 요청**

![](/assets/img/2025-08-23/browser-http-cache-3.png)

대표적인 재검증 요청 헤더들로는 아래와 같은 헤더가 있다.

1. If-None-Match : 캐시된 리소스의 `ETag` 값과 현재 서버 리소스의 ETag의 값이 같은지 확인한다.
   1. 정밀도가 매우 높다 _ ETag는 직접 생성된다
2. If-Modified-Since : 캐시된 리소스의 `Last-Modified`(최종 수정시간)값 이후에 서버 리소스가 수정되었는지 확인한다.
   1. 정밀도가 낮다 _ 서버/클라이언트 시계 차이의 영향이 존재할 수 있다.

예시 흐름)

1. 클라이언트가 `/profile.png` 요청
2. 서버 응답

   ```javascript
   200 OK
   ETag: "abc123"
   Content-Type: image/png
   ...
   ```

3. 클라이언트는 `ETag: "abc123"` 을 저장함
4. 클라이언트의 `/profile.png` 재요청

   ```javascript
   GET /profile.png
   If-None-Match: "abc123"
   ```

5. 서버가 리소스를 확인하고 변경이 없다면

   ```javascript
   304 Not Modified
   ```

## Pragma 헤더

Pragma는 HTTP/1.0 헤더이다. Pragma: no-cache는 캐시가 검증을 위해 원래 서버에 요청을 강제한다. Cache-Control : no-cache와 유사하지만, Pragma는 HTTP 응답에 대해 명세되지 않았으므로 일반적인 HTTP/1.1 Cache-Control 헤더를 신뢰성있게 대체할 수 없다.

## 캐시의 위치

![](/assets/img/2025-08-23/browser-http-cache-4.png)

CDN과 같은 중간 서버를 사용할 때 캐시는 여러 곳에 생길 수 있다. 서버가 가지고 있는 원래 응답을 CDN이 캐시한다. CDN의 캐시된 응답은 사용자 브라우저가 다시 가져와서 캐시한다.

요약 : HTTP 캐시는 여러 레이어에 저장될 수 있다.

### CDN Invalidation

CDN Invalidation은 CDN에 저장되어있는 캐시를 삭제한다는 의미이다. 브라우저의 캐시는 다른 곳에 위치하기 때문에 **CDN 캐시를 삭제한다고 해서 브라우저의 캐시가 삭제되지 않는다.**

경우에 따라 여러개의 중간 서버나 CDN이 있는 경우, 전체 캐시를 날리기 위해선 중간 서버 각각에 대해 캐시를 삭제해야 한다. 그러나 한번 저장된 캐시는 지우기 어렵기 때문에 Cache-Control의 max-age값을 신중히 설정해야 한다.

### s-maxage

중간 서버에서만 적용되는 max-age값을 설정하기 위해 s-maxage값을 사용할 수 있다.

예) Cache-Control: s-maxage=31536000, max-age=0

CDN에서는 1년동안 캐시 유지, 브라우저에서는 매번 재검증 요청을 보내도록 설정할 수 있다.
