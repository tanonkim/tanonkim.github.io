## 결제는 됐는데 줄 상품이 없었다

프로 스포츠 구단의 공식 앱을 만드는 팀에 개발자로 입사한 직후였다. 앱에서 한정 수량의 디지털 상품을 판매했는데, 판매가 열리자 동시 접속자가 3,000명을 넘었다.

그리고 재고가 맞지 않았다. 준비한 수량보다 많은 주문이 결제됐다. 품절 안내를 받았어야 할 사람에게 결제가 이루어졌고, 그 사람에게 줄 상품은 없었다.

관리자 화면의 데이터부터 맞지 않았고, 고객 문의가 쏟아졌다. 그 무렵 하루 업무의 90% 이상을 고객 응대에 썼다.

수습은 사람 손으로 했다. 초과 결제된 분들 가운데 환불을 요청한 분께는 환불해 드렸고, 그렇지 않은 분들께는 상품을 추가로 발행해 전달했다.

원인으로 가장 유력했던 것은 동시성이었다. 같은 재고를 여러 요청이 동시에 읽고, 각자 "아직 남아 있다"고 판단한 것이다. 다만 그때 나는 그것을 확인하고 설명할 방법을 몰랐다. "사람이 몰려서 그랬다"까지는 말할 수 있었지만, 왜 몰리면 재고가 틀어지는지, 어디를 고쳐야 다시는 안 틀어지는지는 정확히 말하지 못했다. 락이라는 개념을 알았다면 더 빠르고 정확하게 고칠 수 있었을 것이다.

이번 주에 그 증상을 내 손으로 다시 만들어 볼 기회가 있었다.

## 같은 증상을 내 코드에서 재현했다

과제로 만들고 있는 커머스의 주문 확정은 이런 순서로 동작한다.

1. 상품의 재고를 읽는다.
2. 주문 수량만큼 남아 있는지 확인한다.
3. 재고를 줄여 저장하고, 포인트를 차감하고, 주문을 확정 상태로 바꾼다.

이 코드에는 이미 비관적 잠금이 걸려 있었다. 잠금이 무엇을 막고 있는지 직접 보고 싶어서, 잠금 조회 5줄을 주석 처리하고 테스트를 돌렸다.

```java
@DisplayName("재고 100, 서로 다른 150명이 1개씩 동시에 주문 확정 → 성공 100 · 재고 부족 50, 재고 0")
@Test
void stock_150Buyers_100Stock() {
    // given: 재고 100개, 구매자 150명이 각자 1개짜리 주문을 만들어 둔다
    ProductModel product = saveProduct("에어맥스", 1_000, 100);
    List<UserModel> buyers = saveBuyers(150, 10_000);
    List<Long> orderIds = createOrders(buyers, product);
    List<String> results = Collections.synchronizedList(new ArrayList<>());

    // when: 150명이 동시에 주문을 확정한다
    try (ExecutorService executorService = Executors.newFixedThreadPool(32)) {
        for (int i = 0; i < 150; i++) {
            int index = i;
            executorService.submit(() -> {
                try {
                    orderCommandUseCase.confirm(buyers.get(index).getId(), orderIds.get(index));
                    results.add(SUCCESS);
                } catch (Exception e) {
                    results.add(e.getMessage());
                }
            });
        }
    }

    // then
    assertThat(count(results, SUCCESS)).isEqualTo(100);
    assertThat(count(results, OUT_OF_STOCK)).isEqualTo(50);
    assertThat(stockOf(product)).isZero();
}
```

결과는 이랬다. (한 번의 실행 결과이고, 남는 숫자는 실행할 때마다 조금씩 달라진다.)

| 상황 | 기대 | 잠금이 없을 때 |
| --- | --- | --- |
| 재고 100, 150명 동시 주문 | 성공 100 · 품절 50 · 재고 0 | 성공 **150** · 품절 0 · 재고 **85** |
| 재고 100, 100명 동시 주문 | 성공 100 · 재고 0 | 성공 100 · 재고 **89** |

재고 100개짜리 상품을 150명이 전부 샀다. 150명 모두 포인트가 차감됐다. 그런데 재고는 85개가 남아 있다. 그날 앱에서 본 것과 같은 모양이다. 품절이었어야 할 50명에게 결제가 됐다.

## 왜 "재고 ≥ 0" 검사로는 못 잡는가

여기서 눈여겨볼 것은 재고가 **음수가 아니라는 점**이다. 85개다. "재고가 0보다 작아지면 안 된다"는 검사는 한 번도 걸리지 않았다.

틀린 것은 재고라는 숫자 하나가 아니라, **성공한 주문 수와 재고 사이의 관계**다.

```
초기 재고 − 성공한 주문의 수량 합 = 최종 재고
     100 −                 150 ≠ 85
```

왜 이렇게 되는지는 요청 두 개만 놓고 보면 분명하다.

| 순서 | 요청 A | 요청 B |
| --- | --- | --- |
| 1 | 재고 100을 읽는다 | |
| 2 | | 재고 100을 읽는다 |
| 3 | 100 − 1 = 99를 저장하고 commit | |
| 4 | | 100 − 1 = 99를 저장하고 commit |
| 결과 | 주문 성공 | 주문 성공, 최종 재고 99 |

두 주문이 성공했는데 재고는 1개만 줄었다. B가 A의 변경을 덮어쓴 것이다. 이것을 갱신 유실(Lost Update)이라고 부른다.

둘 다 "재고가 충분한가?"를 100이라는 값으로 판단했다. 판단 자체는 틀리지 않았다. **판단에 쓴 값이 이미 옛날 값이었을 뿐이다.** 150명이 몰리면 이 일이 수십 번 겹치고, 재고는 실제로 팔린 만큼 줄지 않으니 품절 판정이 영영 나오지 않는다.

## @Transactional도 격리수준도 막아 주지 않았다

처음에는 이 부분이 이해되지 않았다. 주문 확정에는 `@Transactional`이 붙어 있고, MySQL의 기본 격리수준은 `REPEATABLE READ`다. 트랜잭션은 서로 격리된다고 배웠는데 왜 깨지는가.

트랜잭션이 보장하는 것은 "내 변경이 전부 반영되거나 전부 취소된다"이다. 요청 A와 B는 각자 그 약속을 지켰다. 둘 다 온전히 commit됐다.

격리수준이 정하는 것은 "다른 트랜잭션의 변경을 **내가 어디까지 보게 되는가**"이다. `REPEATABLE READ`는 트랜잭션에서 처음 조회한 순간의 사진을 찍어 두고, 끝날 때까지 그 사진을 보여 준다. 터미널 두 개로 확인해 보면 이렇다.

| 순서 | 터미널 A | 터미널 B (`REPEATABLE READ`) |
| --- | --- | --- |
| 1 | | `BEGIN;` `SELECT stock …` → 5 |
| 2 | `UPDATE … SET stock = 4` (commit) | |
| 3 | | `SELECT stock …` → 여전히 **5** |
| 4 | | `COMMIT;` 뒤 다시 조회 → 4 |

B는 A가 바꾼 뒤에도 5를 본다. 내가 보는 값이 흔들리지 않는다는 뜻이지, **내가 본 값이 아직 최신이라는 뜻이 아니다.** 오히려 옛날 값을 일관되게 보여 주기 때문에, 그 값으로 계산해 저장하면 갱신 유실이 난다.

같은 실험에서 조회를 `SELECT … FOR UPDATE`로 바꾸면 결과가 달라진다. 잠금 조회는 사진이 아니라 **최신 commit 값**을 읽고, 다른 트랜잭션이 그 행을 잡고 있으면 끝날 때까지 기다린다.

정리하면 격리수준은 읽기의 규칙이고, "읽고 → 판단하고 → 쓰는" 구간을 한 번에 한 요청만 지나가게 하는 것은 별도의 장치가 필요하다.

## 비관적 잠금을 고른 이유와 비용

그 장치로 네 가지를 비교했다.

| 방식 | 충돌을 다루는 방법 | 비용                                                                                                             |
| --- | --- |------------------------------------------------------------------------------------------------------------------|
| 비관적 잠금 | 읽을 때 행을 잠그고, 다른 요청은 기다렸다가 최신 값으로 판단한다 | 기다리는 요청이 DB 커넥션을 붙잡는다                                                                             |
| 낙관적 잠금 | 저장할 때 버전이 바뀌었으면 실패시키고 다시 시도한다 | 충돌이 잦으면 재시도가 쌓인다                                                                                    |
| 조건부 UPDATE | 검사와 차감을 SQL 한 문장에 넣는다 | 한 문장으로 표현되는 규칙에만 쓸 수 있다                                                                         |
| Redis 분산 락 | DB 밖(Redis)에 "지금 내가 처리 중"이라는 표시를 두고, 표시를 얻은 요청만 진행한다 | Redis라는 의존이 하나 늘고, 락의 만료 시간과 트랜잭션의 순서를 직접 맞춰야 한다 (지금 단계에선 투 머치라고 판단) |

조건부 UPDATE는 이런 모양이다.

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 3
  AND stock >= 1;
```

바뀐 행이 1개면 성공, 0개면 재고 부족이다. `UPDATE`가 행을 잠그고 그 순간의 최신 재고로 조건을 검사하므로, 읽기와 쓰기 사이의 틈이 아예 없다.

나는 비관적 잠금을 골랐다. 과제의 가정은 **서버 하나, DB 하나**였고, 한정 수량 상품에 요청이 몰리는 상황을 떠올렸다. 충돌이 잦다면 재시도보다 기다리는 쪽이 낫다고 봤다. 그리고 주문 확정은 재고만 보지 않는다. 가격이 바뀌었는지, 상품이 삭제됐는지를 함께 확인하고 포인트까지 같은 흐름에서 판단하므로 SQL 한 문장에 담기 어려웠다.

```java
public List<ProductModel> findAllByIdsForUpdate(Collection<Long> ids) {
    return queryFactory.selectFrom(PRODUCT)
            .where(PRODUCT.id.in(ids))
            .orderBy(PRODUCT.id.asc())
            .setLockMode(LockModeType.PESSIMISTIC_WRITE)   // SELECT … FOR UPDATE
            .fetch();
}
```

잠금을 되돌리고 같은 테스트를 돌리면 성공 100 · 품절 50 · 재고 0이 나온다.

Redis 분산 락을 고르지 않은 이유도 적어 둔다. 분산 락은 이번에 직접 적용해 보지 않았고, 아래는 설계하며 비교한 내용이다.

- **DB 락은 행에 걸리고, 분산 락은 약속에 걸린다.** DB 락은 같은 행을 바꾸려는 SQL을 DB가 직접 기다리게 한다. 분산 락은 "이 키를 먼저 얻고 들어가자"는 약속이라, 그 약속을 지키지 않는 경로가 하나라도 있으면 그 경로는 그냥 통과한다.
- **락이 풀리는 시점이 다르다.** DB 락은 commit과 함께 풀린다. 분산 락은 트랜잭션 밖에서 먼저 얻고, commit이 끝난 뒤에 풀어야 한다. 순서가 바뀌어 commit 전에 락이 풀리면 다음 요청이 아직 반영되지 않은 옛 재고를 읽는다.
- **만료 시간이 있다.** 서버가 죽어도 락이 영원히 남지 않도록 만료 시간을 두는데, 처리가 그보다 길어지면 락이 먼저 풀려 두 요청이 동시에 들어간다.
- **교착을 대신 풀어 주지 않는다.** 여러 상품을 서로 다른 순서로 잠그면 DB는 교착을 감지해 한쪽을 끝내 주지만, Redis에는 그런 감지기가 없어 둘 다 대기 시간이 끝날 때까지 기다린다. 키를 정렬해서 얻는 것이 필수다.

재고가 DB 하나에 있고 서버가 하나인 지금 구조에서는 DB 락만으로 충분했다. 분산 락이 필요해지는 것은 보호할 대상이 한 DB에 있지 않을 때, 또는 요청이 너무 몰려 DB 앞에서 미리 줄을 세워 커넥션을 아껴야 할 때다. 그때도 DB 락을 빼는 것이 아니라 그 앞에 더하는 쪽을 생각하고 있다. 줄은 Redis에서 서고, 최종 판단은 DB가 한다.

실험하다가 배운 것이 하나 더 있다. 처음에는 상품 잠금 한 줄만 주석 처리했는데 테스트가 그대로 통과했다. 잠금을 뺐는데 왜 안 깨지는지 한참 봤다. 내가 주석 처리한 것은 관리자가 상품을 수정할 때 쓰는 조회였고, 주문 확정은 다른 조회 메서드로 상품을 잠그고 있었다. "상품 잠금"은 한 군데가 아니었다. 같은 행을 바꾸는 경로가 여러 개면 그 모두가 잠금에 참여해야 하고, 하나라도 빠지면 그 경로가 나머지의 변경을 덮어쓴다.

## 아직 확인하지 않은 것

이 글에서 확인한 것은 재고와 주문과 포인트가 **같은 DB에 있는** 구조의 이야기다. 그래서 DB 행 잠금 하나로 "읽고 → 판단하고 → 바꾸는" 구간을 보호할 수 있었다.

내가 겪었던 서비스는 여러 서비스로 나뉜 구조(MSA)였다. 처음에는 그래서 분산 락이 답이라고 생각했다. 그런데 이번에 공부하며 생각이 바뀌었다. 재고는 한 DB에 있었고, DB 잠금은 서버가 몇 대든 그 행 앞에서 요청을 한 줄로 세운다. 초과 판매만 놓고 보면 재고를 차감하는 그 한 곳에서 행 잠금이나 조건부 UPDATE로 막을 수 있었을 것이다.

서비스가 나뉘어서 정말 어려워지는 것은 다른 문제다. 결제와 재고 차감이 서로 다른 서비스에 있으면 한 트랜잭션으로 묶을 수 없고, 한쪽만 성공했을 때 되돌리는 방법을 따로 설계해야 한다. "결제는 됐는데 상품이 안 나갔다"에는 이 문제도 섞여 있었을 수 있다. 이 부분과 분산 락은 아직 공부하는 중이라 여기서 답을 쓰지 않는다.

비관적 잠금의 비용도 재 보지 않았다. 기다리는 요청은 DB 커넥션을 붙잡는데, 3,000명이 몰렸을 때 그 대기가 얼마나 되는지는 부하를 걸어 봐야 안다.

그래도 하나는 달라졌다. 그날 내가 물었어야 할 질문을 이제는 안다. "재고가 음수인가?"가 아니라 "성공한 주문 수와 줄어든 재고가 맞는가?"였다.
